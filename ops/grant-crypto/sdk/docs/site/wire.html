Wire format

What travels on the wire

The normative, language-neutral description of the bytes that cross between implementations, so independent implementations interoperate and cannot silently drift. Every structure carries a suite identifier, bound into the AEAD additional-authenticated-data of the structure it labels — so a suite cannot be silently downgraded, and an implementation that does not recognise a suite fails closed rather than misparsing.

An unknown or absent suite is a hard, fail-closed error (UnsupportedSuite) — distinct from a decryption failure, and returned before any key operation, so it leaks nothing about keys.

v2 hybrid wrap (inert)

The v2 DEK wrap runs both a classical X25519 ephemeral-static exchange and an ML-KEM-768 encapsulation, combining the two shared secrets so confidentiality holds if either KEM is unbroken (harvest-now-decrypt-later defence). The v2 wrapped entry carries { epk_x25519 (32B), mlkem_ct (1088B), nonce, wct } and needs a hybrid recipient key (an X25519 point plus an ML-KEM encapsulation key) — a PKI extension over today’s EC SVIDs. The combiner is X-Wing (draft-connolly-cfrg-xwing-kem, external review 2026-07-29):

Implemented directly over ml-kem + x25519-dalek (the x-wing crate needs a rand_core version that conflicts with the AES-GCM/P-256 stack; the construction is byte-identical, with a later migration to the crate). It is inert and round-trip-tested only. See Security → FIPS + PQC for the gates that would move it to live.

Bundle authentication

The key service signs the bundle; a member MUST verify before trusting any wrapped key. For v1 the signature is ECDSA-P256 over SHA-256 of the canonical transcript (a post-quantum suite moves this to ML-DSA):

signer binds the claimed identity, so a signature cannot be moved to another signer; the verifier maps signer to a trusted public key. signer_svid is an OPTIONAL, self-describing carrier of that key: the key-service’s own SVID (PEM), so a member can validate it against the SPIRE root and the expected key-service SPIFFE id and obtain the verifying key without a side channel — and an old cached bundle stays verifiable after the key-service rotates its identity. It is deliberately excluded from the transcript, so its presence or absence never changes sig or the conformance vectors; a member MAY instead be handed the verifying key out of band. Verification failure, an absent signature, or the wrong key is BadSignature — the member treats the bundle as untrusted and unwraps nothing.

Conformance

An implementation is conformant if, for a fixed suite and fixed key material, it (a) produces envelopes/wraps/bundles another implementation opens, and (b) opens those another implementation produced, with identical accept/reject decisions on the negative cases (wrong key, wrong generation, wrong release-set, wrong topic, tampered bytes, unknown suite, bad signature).

The canonical decrypt-direction test vectors live in the SDK at envelope/testdata/vectors/ (committed fixed keys + produced artifacts + accept/reject cases). The consumer order every implementation must follow is verify → slot → unwrap → open:

  1. if a trust identity is supplied, verify the bundle signature — reject on failure;
  2. find the member’s slot — reject if absent (not in the audience);
  3. unwrap the DEK with the member key — reject on failure;
  4. open the envelope with the case key-expression — reject on failure.

Both the Go reference and the Rust production reference validate against these vectors; the Rust read side is byte-compatible and passes all cases. No vector pins ECDSA sig bytes (signing is nondeterministic across backends); vectors verify signatures. The boundary of what conformance proves — read-interop versus the separately-gated write side — is on the Security page.
