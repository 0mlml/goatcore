Concepts

The mental model

Six ideas carry the whole library: release-sets and generations, data keys and wrapping, bundles, the key-less platform, revocation as rotation, and forward secrecy as an endpoint property. Once these click, the API reads as the obvious shape.

Release-sets and generations

Data is grouped into a release-set (rs) — a named stream that a defined audience is allowed to read, for example example-set. Within a release-set, keys advance by generation (gen), a monotone counter. Each (rs, gen) pair has exactly one symmetric data key. When the audience changes — someone joins, someone is revoked — the key service publishes a new generation. Old generations are never rewritten; a member simply stops being included in new ones.

Data keys (DEKs) and wrapping

A DEK (data encryption key) is a fresh 256-bit symmetric key for one (rs, gen). Payloads are sealed under the DEK with AES-256-GCM. Members never receive the DEK in the clear: the key service wraps it to each member’s public key — an ephemeral-static ECDH exchange to the member’s enrollment key, deriving a key-encryption key that encrypts the DEK just for that member. A wrap is bound to both public keys, so it cannot be re-presented for a different recipient. The exact bytes are in the wire format.

Bundles

A KeyBundle is what the key service publishes for one (rs, gen): the wrapped DEK for every member of the audience, keyed by member id, plus the service’s signature. A member finds its own slot in the bundle, unwraps the DEK with its private key, and keeps it. An outsider has no slot — there is simply nothing in the bundle for them to unwrap. Bundle assembly is fail-closed: if any single member’s wrap fails, the whole bundle is aborted rather than published partial.

Why the platform can never decrypt

The key service mints a DEK, wraps it to each currently-authorized member, publishes the bundle, and drops the DEK. It retains only a signing key and a generation counter. It holds no DEK and no member private key, so it is structurally incapable of reading any payload — and it cannot hand a latecomer access to data that was not encrypted to them at publish time, because it has nothing to hand over. The fabric carries wrapped bundles and ciphertext: locked boxes it never reads.

Sealing and opening

A producer is itself a member of the release-set. It acquires a seal-capable key by unwrapping its own slot in the highest generation it can see, then seals each message under that key. Sealing takes no recipients — the audience was already resolved by the key service when it built the bundle. Every message binds a context (the data topic / key expression) as additional-authenticated-data, so a message sealed for one topic cannot be opened on another, even by an authorized member.

A consumer follows a fixed order: verify the bundle signature, find its slot, admit (unwrap and retain the DEK for that (rs, gen)), then open messages. A message is openable only if the consumer holds the key for its generation. This order is enforced by the shape of the API, not by caller discipline.

Revocation is rotation

There is no “revoke” operation that reaches back and unmakes access. Instead, to revoke a member the key service publishes a new generation whose audience omits them. The revoked member keeps the older-generation keys it already holds (it can still open the traffic it was legitimately given), but it is not in the new bundle, so it can never admit or open the new generation.

Forward secrecy as an endpoint property

Because a DEK is wrapped to a member’s static, long-term enrollment key and bundles are retained, a future theft of that member’s own private key could decrypt that member’s own past traffic. That residual is closed by destructive rotation: the member rotates its enrollment key and zeroizes the retired private key. Only new generations wrap to the new key; there is no re-wrap path. The loss of the ability to re-fetch pre-rotation history is the forward secrecy.

This property lives and dies in the receiver’s software, not on the wire and not on the platform. That is why it is called endpoint-enforced: nothing central can grant it and nothing central can take it away.

Rotate has two policies

Destroy (the default) drops the retired key and re-wraps nothing — full forward secrecy. KeepAccess is an explicit member-side opt-out: before dropping the old key, it locally re-wraps the member’s own still-live DEKs to the new key, so those generations stay readable — and it is labeled plainly as reducing forward secrecy for them. The platform is never involved either way; it holds nothing to re-wrap. See Security → Rotation.

Destroy-by-default

Every default in the library leans toward the safe behavior: DEKs are fetched, used, and dropped rather than persisted; rotate defaults to Destroy; and the seal path enforces a message-count cap below the AES-GCM nonce-collision bound, refusing to seal past it rather than risking nonce reuse. The easy path is the secure path — the details are on the Security page.
