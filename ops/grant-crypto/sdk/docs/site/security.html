Security

What holds, and where the edges are

This page is deliberately honest. It restates the invariants, then walks the parts that are easy to overstate — the zeroization ceiling, the seal cap, rotation’s tradeoff, FIPS and post-quantum posture, and the exact boundary of what conformance proves. If a claim is qualified below, the qualification is the point.

Invariants

  • The platform holds no keys. The key service mints, wraps, publishes, and drops the DEK. Its API exposes no function that returns plaintext or a DEK.
  • Only members decrypt, in-process. Plaintext is returned only to the holder of the member identity key; a non-member has no slot and admit fails closed.
  • The producer is not a key authority. seal takes no recipients; a producer seals under a key unwrapped from its own bundle slot.
  • Forward secrecy is endpoint-enforced. Default rotation destroys the retired private key with no re-wrap. The platform can never re-wrap — it holds nothing to re-wrap.
  • Suite-agnostic by construction. No algorithm, nonce, or RNG appears in any public signature; the suite id travels in the data and is AAD-bound, so a suite cannot be silently downgraded.
  • Fail closed, quietly. An unknown suite fails before any key operation; a missing slot is a normal outcome; every other failure is a reject, and error variants are advisory, never an oracle.

Capability vs reject — the error design

The error taxonomy is designed so that error variants never leak key information. Three classes:

  • Capability signal — UnsupportedSuite means “I do not implement this suite,” raised before any key operation. It is safe to branch on: it says nothing about keys.
  • Normal outcome — NoSlot means “not in the audience / no key held for this generation.” It is expected, not a failure.
  • Reject — Decrypt, Unwrap, BadSignature, Malformed are authenticated-failure rejects. The distinction between them is advisory; a caller must not treat any of them as a decrypt oracle. Never build control flow that reveals which reject occurred to an untrusted party.

RotationRequired is a fourth, write-side case: a local refusal to seal past the cap. It changes nothing on the wire and is distinct from Decrypt — it is never a decrypt oracle.

The zeroization ceiling

Key material is wiped on dispose and drop — but zeroization in a systems language has honest limits, and the SDK states them rather than implying a guarantee it cannot keep. Within the ceiling: identity scalars, held DEKs, stream-key DEKs, and buffer contents are wiped on dispose/drop, and local key copies are wiped after use. The ceiling itself:

What zeroization does not cover
  • Move copies. Rust move semantics can leave stack copies of a value that the zeroize path never sees.
  • By-value returns at the conformance layer. A [u8; 32] returned by value (required by the conformance/roundtrip layer) leaves an uncovered caller copy at that boundary.
  • The AES key schedule. Expanding a key into AES round keys produces a schedule the zeroize story never touches.
  • Plaintext and receipts in a managed language. Plaintext returned by open and envelopes returned by seal are ordinary bytes in Go/Python/TS — the binding does not zeroize what it returns to you. Treat them as caller-managed sensitive data: minimize copies, drop references promptly.
  • No mlock / guarded allocation. Key pages are not locked or guarded by default; this is a possible later opt-in, never a silent promise.

The seal cap

v1 seals every message with a fresh random 96-bit nonce under a shared per-generation DEK, so the risk to manage is a nonce collision. After q seals the collision probability is approximately q² / 2⁹⁷. NIST SP 800-38D-style guidance keeps q ≤ 2³² (collision ≈ 2−33). The SDK defaults an order of magnitude tighter:

DEFAULT_SEAL_CAP = 2²⁴ = 16,777,216 seals

A 256× (2⁸) margin below 2³², giving a collision probability of about (2²⁴)² / 2⁹⁷ = 2−49 at the cap. At the cap, seal refuses with RotationRequired rather than risk nonce reuse; remaining() surfaces the approach well before the refusal.

Three properties keep the cap from being defeated by accident:

  • Cumulative within the process. The count lives in a process-global counter keyed by (rs, gen), not in the stream key. So the natural “hit the cap, re-acquire, continue” path cannot silently reset the budget — re-acquiring the same generation carries the count forward.
  • Fresh budget only on a new generation. A different generation is a different budget line: rotation legitimately re-keys the DEK, so its count starts fresh. Across a process restart the counter is empty again; the systemic guarantee there is the key service publishing new generations.
  • Monotone, tighten-only. set_cap / with_cap take min(current, requested). A later request can lower the cap, never raise it back — and since it starts at the default, never above the default.

Honest concurrency note Concurrent producers sealing the exact same (rs, gen) in one process may each read a slightly stale local count between the check and the write-through, so the effective cap is approximate under that unusual concurrency — never loose enough to matter against the 2⁸ margin.

Rotation: Destroy vs KeepAccess

Rotation is entirely member-side; the platform is never involved (it holds no keys and can never re-wrap). Two policies, stated plainly:

PolicyWhat it doesForward-secrecy effect
Destroy (default)Drop the retired private key; re-wrap nothing. The member loses the ability to re-fetch pre-rotation history from retained bundles.Full forward secrecy. That loss is the forward secrecy: a future theft of the new key reveals nothing sealed to the old one.
KeepAccess (opt-out)Before dropping the old key, locally unwrap the member’s still-live DEKs and re-wrap each to the new public key, on this machine.Reduces forward secrecy for those generations — a theft of the new key now reaches them. Choose it only when you genuinely need continued access to that history.

Every rotation emits a RotationReceipt: a structured, self-dating fact (member id, count of now-unreadable pre-rotation generations, count re-wrapped, an absolute RFC3339 UTC timestamp) — never time-relative prose. Persist it to your ledger.

FIPS + PQC posture

The default backend is RustCrypto (pure Rust, non-FIPS). A fips build feature re-bases the primitive stack onto aws-lc-rs / aws-lc-fips-sys — a real re-base plus a full conformance re-run, not a flag — and the pair is pinned and verified by compiling.

SuiteStatusFIPS
v1-ecdh-p256implementedFIPS-capable (under the fips feature): AES-256-GCM payloads; DEK wrapped by ephemeral-static ECDH P-256 → HKDF-SHA256; bundle signed ECDSA-P256/SHA-256.
v2-x25519-mlkem768provisional, inertBeyond-FIPS defense-in-depth — never a FIPS-mode tier. An X-Wing hybrid (X25519 + ML-KEM-768) for harvest-now-decrypt-later defence.

v2 stays inert until three gates pass: the exact draft/RFC revision is pinned in the wire spec, spec KATs (not self-roundtrip) gate it, and any combiner-affecting change mints a new suite id. Shipping a new suite is a separate, audit-gated decision; the API merely accommodates it without a break. See the wire format for the suite table.

WASM stance

WASM is deferred, and it is never key custody. WASM cannot honor the zeroize and forward-secrecy defaults the rest of the SDK provides, so if it is ever shipped it will be an explicitly-named, reduced-assurance interop tier — not a place keys live. It is not part of v1.

What conformance proves — and what it does not

“One implementation” is an honest claim only because it is scoped honestly. There are two separate gates, and neither borrows the other’s coverage:

  • Read side (proven byte-for-byte). The shared decrypt-direction vectors are a required CI merge gate for the core and every binding — byte-exact accept/reject parity, including the negative cases (wrong key, wrong generation, wrong release-set, wrong topic, tamper, unknown suite, bad signature). This proves read-interop.
  • Write side (cannot be vector-pinned). The write path is deliberately nondeterministic (fresh random nonces), so vectors cannot cover it. Instead, every binding seals through itself and re-opens the result (a roundtrip, including the wrong-topic fail-closed case) and asserts nonce freshness on sealed output. This proves write safety.
Stated so the claim can’t outrun the tests

Two write-side strengthenings are queued follow-ups, not yet built: a deterministic-RNG injection seam in the core for true uniqueness assertions, and a binding-sealed → Go-reference-opened cross-implementation leg. Today the Go-sealed → Rust-opened direction is covered by the vectors themselves. Vectors prove read-interop; the RNG-injection work will prove write uniqueness — neither claim borrows the other’s coverage.

One structural divergence in the reject class is expected and allowed, stated so it can’t creep: a wrong-generation envelope rejects as Decrypt through the reference’s unwrap-then-open shape but as NoSlot through the SDK keystore’s (rs, gen)-indexed shape (no DEK is held for that generation, so the reject happens before any key operation). Conformance runners accept {Decrypt, NoSlot} for that one case only; every other case asserts the exact class. A binding that fails either gate does not ship.
