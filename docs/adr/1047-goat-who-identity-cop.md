# ADR 1047 — `goat who`: a searchable identity common operating picture (the roster-browser altitude)

**Status:** Accepted — built in `goat-cli` (a new `goat who` command + tui module + a lazy `access who` fetcher); **extended to the cross-layer COP in 0.4.9** (see the 2026-06-17 addendum: portal-side W/R fix + bulk `access roster` endpoint + cross-layer `STATE` + activity-first default). Ships dark; ZAGROS live-fire is operator-gated (same posture `goat top` shipped under before M-067).
**Repo scope:** goat core (`goat-cli`: `cmd/who.rs` + `tui/who.rs`, reusing `panoscope-core` `AliasRegistry`/`EnvelopeRegistry`/`PortalClient` and the shared `health_wire` footprint/presence wire types)
**Related:** [ADR 1046](1046-goat-top-live-fabric-dashboard.md) (the usage-leaderboard sibling this contrasts with) · [ADR 1026](1026-data-access-common-operating-picture.md) (the `access who` forward query it browses) · [ADR 1039](1039-slot-alias-display-layer.md) (alias display, fail-closed) · [ADR 1040](1040-zenoh-advanced-pubsub-liveliness-adoption.md) gap 3 (presence) · [ADR 1045](1045-qos-throughput-envelopes.md) (the BAND verdict) · [ADR 1019](1019-goat-cli-unified-operator-binary.md) (the binary) · [`goat-who-identity-cop.md`](../design/goat-who-identity-cop.md) (the design)

## Plain-language summary

`goat who` is the `top(1)` of *identities*. Where `goat top` ranks producers by how loud they are, `goat who` is a **searchable roster browser**: a left-pane list of every identity in the goatnet — declared in the registry or merely observed live — that you filter and arrow through, beside a detail pane that shows the selected identity's permissions (from the Data-Access COP) and its live behavior (presence + footprint). It is a **pure consumer + read-only portal queries**: no producer, no enforcement, no mint, no revoke. It inherits the environment-health honesty discipline unchanged — never a state it cannot ground (`—`/dim for absent, `·` for not-yet-fetched permissions, the truncated UUID when no alias is known).

## Context

- An admin's everyday question — *"who is in this goatnet, what may each of them do, and what are they doing"* — had **no single surface**. `goat access who <id>` answers it for one id at a time (no roster, no navigation, no live usage); `goat presence` shows liveliness only; `goat top` is a usage leaderboard that only lists *producers*, ranked by rate, as rows of numbers.
- Every input already exists and is decoded today: portal `GET /api/vendors` + `GET /api/aliases` (the declared roster), `GET /api/access/who` (the [Data-Access COP](../design/data-access-cop.md) forward query), and the `ops/fabric/footprint/**` + `ops/presence/health/**` bus topics (`goat top`/`goat health`/`goat presence` already consume them). This is a new *composition*, not new substrate.
- `goat top` (ADR 1046) established the proven shape — a producer async task feeding an mpsc channel, a `spawn_blocking` ratatui loop with guaranteed teardown, a pure view model shared by the interactive screen and a `--once` plain renderer, read-only random-ZID session. `goat who` reuses it.
- The user's framing was explicit and load-bearing: this surface must lean **searchable, not usage-ranked**. A leaderboard is the wrong default for "who is here."

## Decision

1. **`goat who` is a roster *browser*, not a dashboard — a distinct idiom from `goat top`.** Master-detail (the k9s / lazygit pattern): a filterable identity list (master) beside a per-identity capability+activity pane (detail). Default sort is **name**, not usage — searchable-first, stable under traffic churn.
2. **The spine is the identity roster = declared ⊕ live.** Union of the portal registry (vendors ⊕ aliases) with every anchor observed live this session (footprint `peer`, presence `write_root`). A live anchor absent from the registry is shown, flagged `live, not in registry` — never silently dropped, never silently promoted to declared.
3. **Permissions are fetched lazily per selection and cached.** A roster of hundreds of actors must not fire one `access who` call per actor on open. The selected identity's `access who` is fetched on demand on a small async fetcher task (fed by the UI loop over a request channel; results return on the same channel the bus subscribers use, so the sync loop never blocks on the portal). An opt-in `a` key drips the whole roster through the fetcher for operators who want the full capability picture at once.
4. **Honesty discipline inherited wholesale.** Computed once in a pure `view_model` shared by both renderers. Live `●`/`○`/dim-`?` grounded only on a current presence token; absent usage → `—` (idle, not `0`); no envelope → `—` band; permissions `·` until fetched and `portal unreachable` (not an empty allow-list) when the portal is down; unknown alias → truncated UUID (alias layer fails closed, ADR 1039). Never a false green, never a guessed count, never a phantom name.
5. **Pure consumer + read-only queries, brokerless-safe.** Subscribes footprints + presence and queries the portal read API. Publishes nothing, enforces nothing, mutates nothing.
6. **Read-only, no mutation, by design.** No revoke / lock / rotate from `goat who` in v1 — a read-only COP must not become a foot-gun. The cut stays `goat admin onboard --revoke` / `goat admin peer`; rotation stays `goat admin rotate`.
7. **TTY-gated interactive screen; `--once` is the scriptable batch path.** Interactive calls `require_tty("goat who")` before session open. `--once` skips the gate and prints one plain-text roster snapshot (name / live / usage / band / registry-membership) — permissions are excluded from `--once` (an N-call-per-identity fetch); the scriptable single-identity capability path stays `goat access who <id>`.

## Alternatives considered

- **Just add a `--tui` flag to `goat access who` — rejected.** That command is single-identity by contract; a roster browser is a different surface with its own state model (the declared-⊕-live fold, the lazy-fetch cache, the live join). Bolting it on would overload one command with two idioms.
- **Make it a `goat top`-style usage leaderboard for identities — rejected.** The user explicitly wanted searchable-first, and a usage rank reshuffles under traffic and omits idle/declared identities entirely — the opposite of "who is in my system."
- **Prefetch `access who` for the whole roster on open — rejected for v1.** One portal call per actor on every launch is a poor open latency and hammers the portal; lazy-on-select + opt-in `a` enrich is bounded and honest (`·` until fetched). Background auto-enrich of the visible window is named as roadmap.
- **Fold operator-action audit into the detail pane now — deferred.** The `ops/audit/operator/<actor>` stream (age-encrypted) exists; surfacing "how an operator used their powers" here is a clean follow-on, not v1 scope.

## Consequences

- A new operator surface for "who is here / what can they do / what are they doing," navigable over SSH with no browser, at zero new bus producers and zero enforcement risk.
- It reuses `goat top`'s proven async-producer + ratatui structure and `panoscope-core`'s portal/alias/envelope clients — no new substrate, one new composition.
- The read-only-by-design stance keeps the mutation surface (revoke/rotate) where it already lives; a future write path is a deliberate, separately-gated decision.
- Roadmap is scoped, not dropped: background auto-enrich, operator-action-audit in the detail pane, and identity-grammar dimension columns once a portal roster endpoint exposes role/affiliation/echelon.
- Live-fire on a sandbox goatnet (ZAGROS) → measurement, operator-gated (not part of this build).

## Addendum (2026-06-17) — the cross-layer COP rework (goat-cli 0.4.9)

A live-ZAGROS review of the 0.4.8 build said *"better, but not true to its purpose."* The defects were in the data model and the product concept, not the rendering. The operator's bar, restated: *"`who` is a quick view + drill-downable tool to see who has **active permissions, what they are, and what they are being used for**, able to look across **NetBird → Ory → SPIRE/SPIFFE → Zenoh** and see role/permissions and **last activity** for any entity."* This addendum extends the decision toward that bar; the §Decision points above are unchanged except where noted.

1. **Permissions are real (the W/R `0/0` fix, portal-side).** The access graph (`internal/access/{graph,query}.go`) computed an identity's writes only from its org's rendered may-write edges and never emitted a slot-pool member's own `<anchor>/**` grant — so on a slot-pool goatnet (ZAGROS, where nearly every actor is a slot member) the whole roster reported zero writes; reads showed `0` because flat community-read was a graph flag the forward query never surfaced. `Who` now emits the `<anchor>/**` namespace write grant for any spine with a write anchor (the pre-baked per-uuid grant, [ADR 1025](1025-zenoh-dynamic-tenant-authz-slot-pool.md)) and reflects community-read as a `**` read grant. A genuine `0/0` now means "onboarded but can write+read nothing" — the F-177 silent-denial surface, flagged `no-grants`.
2. **Permissions are instant (responsiveness).** New bulk endpoint `GET /api/access/roster` assembles a slim cross-layer summary (W/R counts + reconcile state + on-mesh / last-activity) for **every** identity in one server-side call; `goat who` seeds the whole roster from it instead of an N-deep per-row `access who` fetch (the ~9 s-per-selection round-trip on the lossy mesh that read as "not responsive"). The per-row `access who` stays — but only to enrich the **selected** row's detail-pane reason lists.
3. **`STATE` means something (no longer uniform "active").** A composed **cross-layer status** — `online` / `on-mesh` / `cut-off` / `no-grants` / `stray` / `active` / `·` — derived from the bulk summary (recon state + mesh `connected`/`on_mesh` + grant counts), so the column varies and each value is actionable. NetBird `last_seen` + `connected` are plumbed from the poller through the graph into the summary.
4. **Default sort flips to activity-first (`live`).** A deliberate, documented reversal of Decision §1's `name` default after the live review asked for a meaningful default — reconciled, not flip-flopped: it is presence-first (not a msgs/s leaderboard, which stays `use`), and `/` search is instant in every mode, so the roster is still searchable-first.
5. **Still designed-not-built:** the **SPIRE/SPIFFE fourth domain** (the graph already joins NetBird + Ory + Zenoh server-side — add a SPIRE source) and **per-layer last-activity** rendering (Ory last-login + SPIRE last-SVID + the mesh `last_seen` *age*, which the endpoint already returns). These complete the four-domain North Star; the roster-summary shape has room for them.

**Status update:** Accepted — 0.4.9 built (portal Go: slot write-grant + community-read + bulk `access roster` + mesh last-seen; goat-cli: bulk-seeded roster, cross-layer `STATE`, activity-first sort, instant detail rollup). ZAGROS live-fire operator-gated.
