## TL;DR (for a layperson)

We already encrypt data so that only the people a data owner *grants* can read it, and — importantly — **no server anywhere holds a key that can decrypt**; only each recipient, on their own machine, with a key only they hold. The one thing that would make it even stronger ("forward secrecy" — a machine seized next year reveals nothing about last year) can't be *forced* by us, because we don't own the recipient's computer the way Signal owns its app. So we win it the other way: **build a genuinely excellent, first-class encryption library that works everywhere and in every language, make the safe behavior the automatic default, and let people adopt it because it's the best tool** — with policy able to *require* the good habits later, once they're already the easy path.

## Context — the verified starting point (no muddle; this is what the code does)

- **The platform holds no decryption keys.** The key-distribution service (`grant-keyd`) mints a symmetric data key (DEK) per `(release-set, generation)`, wraps it to each currently-authorized member's public key, publishes the wrapped bundle, and **drops the DEK** — it retains only a signing key and a generation counter (`grant-crypto/rs/src/service.rs`: *"It never retains a DEK — each is minted, wrapped into the bundle, and dropped."*). It cannot decrypt anything.
- **Only members decrypt, in their own process, with keys only they hold.** A member's enrollment private key never leaves its machine; it unwraps a DEK from a bundle **only if the bundle was wrapped to it** (`datapath.rs` `KeyStore::admit` returns nothing to a non-member) and opens messages with `open`. The fabric carries wrapped bundles + ciphertext — locked boxes it never reads.
- **Need-to-know is already maximal.** A latecomer / new member / outsider is simply not in a generation's bundle, and the key service holds no DEK to hand them retroactively — so **no one, including the platform, can grant read access to data that was not encrypted to them at publish time.** (Building "backfill" — letting a latecomer read unaddressed history — would require the key service to *start retaining* DEKs, a deliberate loosening; it is **declined**, and is not on this track.)
- **Forward secrecy is the one narrow residual, and it is an *endpoint* property.** Because a DEK is wrapped to a member's *static, long-term* enrollment key and the wrapped bundles are retained, a *future* theft of that *member's own* enrollment private key could decrypt that member's *own* past. That is closed by **destructive rotation** — the member rotating its enrollment key and **zeroizing the retired private key** (only new generations wrap to the new key; there is no re-wrap path, verified). Forward secrecy therefore lives and dies in the *receiver's software*, not on the wire and not on the platform.
- **We do not own the receiver's endpoint.** Signal achieves continuous forward secrecy because it owns the whole app end-to-end and can guarantee the key deletion. On a fabric of **sovereign** members running their own software, we cannot *force* that. What we can do is make the secure behavior the effortless default in tooling so good that sovereigns choose it — with compliance policy as a later backstop, not the sales pitch.
- **Decryption today is reference-grade, not a first-class SDK.** It runs in each member's own process against a library: **Python** (`hello-galaxy-grant-encryption/lib/grant_enc.py`, a ~250-line teaching reference), **Rust** (`ops/grant-crypto/rs`, the production core: `KeyStore::admit` + `open`), and **Go** (`ops/grant-crypto/envelope` + the `gce` proof CLI). `goat-client` does **not** integrate decryption. There is no canonical, cross-platform, multi-language SDK that a heavy community could build on — and no library that makes the forward-secrecy hygiene a default.
- **A durable spine already exists.** `ops/grant-crypto/WIRE-FORMAT.md` (the wire spec, with the suite-agility hinge) and the conformance vectors (`cmd/vectorgen`, `conformance/`) are the cross-implementation contract; the Rust core is production-grade. The SDK is a promotion of existing assets, not a green field.

## Decision (proposed)

Make grant-keyed encryption — **both sides: sealing (producer) and opening (consumer)** — a **first-class, cross-platform, multi-language SDK whose safe default is forward-secrecy hygiene**, so that matching Signal-grade forward secrecy on endpoints we don't own is achieved by **adoption + defaults + optional policy**, not by force.

**A general-purpose library, not a goat appendage.** The core does one thing — grant-keyed envelope **encryption and decryption** (`seal`/`open`, wrap/unwrap, the consumer key store, destructive rotation, the wire format) — and does it **transport- and deployment-agnostic, with no dependency on Zenoh, the portal, SPIRE, or ZAGROS.** It is usable standalone, by anyone, against any transport. **goat/ZAGROS is a first-class but strictly optional integration layer** — thin adapters for fabric bundle transport, portal recipient-key resolution, and SPIRE identity — that sits *on top* of the core: excellent support, zero coupling, never opinionated into the core. A team that has never heard of goat should reach for this library on its own merits.

**The bar — built for developers, meant to last.** This is the same care we took with `goat-cli` for its operators, applied to a library the world builds on: **efficient, clean, and as simple as the problem allows; clear and obvious to pick up; a joy to use.** Where real cryptographic sophistication is required, we go there **deliberately and with open eyes** — never accidental complexity, never sophistication for its own sake, and never a rabbit-hole that only its authors love. The measure of success is that a working developer reaches for it because it is genuinely excellent — a piece of infrastructure that is still the obvious choice **decades from now**, not a clever artifact. Every decision below serves that bar; if a choice makes the common case harder to get right, it is the wrong choice.

**Don't reinvent unless we can do better.** Before building, do a deliberate review of the best crypto libraries and SDK tooling in the world and **adopt their proven approaches, and cannibalize their code where the license permits** and a part is genuinely superb. Default to reuse — but **reinvent deliberately where we can demonstrably surpass the state of the art**, and when we do, say plainly *why* it's better (measured, not asserted). We are not chasing novelty for its own sake, nor settling for second-best out of deference; we assemble the best existing ideas and improve on them only where the improvement is real. License discipline is strict: we vendor only **permissive**-licensed code (Apache-2.0 / MIT / BSD / ISC) compatible with a library the world embeds — no copyleft contamination — and attribute faithfully. Concretely:

1. **One owned core, many bindings — the core is Rust, and that is a deliberate, defensible choice.** A single security-critical crypto core must (a) be memory-safe (a use-after-free in a key path is catastrophic), (b) reliably **zeroize** key material, (c) ride a **FIPS**-validated primitive stack, (d) compile to **every OS/arch and to WASM**, and (e) be **consumed cleanly from every language**. The real field is C, Go, or Rust:
   - **C** — the universal ABI, but memory-*unsafe* with no zeroization guarantees; wrong substrate for security-critical code a whole community leans on. (We still expose a C *ABI* — below — without writing the core *in* C.)
   - **Go** — has a reference today (`gce`), but is a poor *consumed* library: cgo-boundary cost, a GC/runtime that doesn't embed cleanly into other languages, and — flagged in the original design decision — no reliable key **zeroization**. Fine for a service, wrong for an embeddable core.
   - **Rust** — memory-safe by construction, first-class `zeroize` *support in the ecosystem* (the current core does not yet zeroize — wiring that, honestly ceilinged, is Phase-1 work, not a property being promoted), best-in-class cross-compilation and C-ABI FFI, and — decisively — **the production core already exists in Rust** (`ops/grant-crypto/rs`), reviewed and conformance-tested. It wins every criterion Rust *can* win today; zeroization and the FIPS backend are the two it must still be *made* to win (critic pass, 2026-08-01).

   So: promote `ops/grant-crypto/rs` to the **canonical core**, expose a **stable C ABI** (the universal interop surface — written in Rust, not C; hand-authored, versioned, opaque-handle — the single audited FFI choke point), and ship **thin hand-written bindings for the committed set — Go, Python, TypeScript/JS — the languages with named consumers**; the C header falls out of the ABI for free. Further languages (C++, .NET/F#, JVM, Ruby, Elixir) and platforms (Windows, WASM) are **demand-gated: added when a real consumer names them, never speculatively** (critic pass — the 8-language matrix was scope without consumers; WASM additionally can never honor the zeroize/FS defaults and, if ever shipped, is an explicitly-named reduced-assurance interop tier, not key custody). Every binding is gated on the `WIRE-FORMAT.md` spec + **conformance vectors** — which prove **decrypt-direction interop byte-for-byte**; write-side safety is separately gated by RNG-injection tests (the write side is deliberately nondeterministic and cannot be vector-pinned). (A different core substrate would have to beat Rust on all five criteria *and* justify discarding a working, audited core — a bar this ADR does not expect met.)
2. **Secure by default.** The SDK **defaults to forward-secrecy hygiene**: data keys held **ephemerally** (fetched-and-used, not needlessly persisted), a **cumulative-message-count rotation cap** enforced (not advisory) with margin below the GCM birthday bound, and **destructive enrollment-key rotation** — rotate the member's leaf (ADR 1044) and **zeroize the retired private key**, with **no re-wrap of anything** — as the default, not a buried option. The stated consequence (surfaced as a structured, self-dating fact): the member loses re-fetch of pre-rotation history — that loss *is* the forward secrecy. A member-side-only `--keep-access` opt-out may locally re-wrap its own still-live DEKs to the new key before zeroizing, labeled plainly as *reducing* FS for those generations; **the platform is never involved — grant-keyd holds nothing to re-wrap** (critic pass F1: any service-side re-wrap would violate the key-less invariant). The easy path is the secure path.
3. **`goat-cli` is a consumer, not the surface.** `goat-cli` (and the portal, integrations, partner kits) become **derivative consumers** of the one SDK — no second implementation, one audited core, zero drift.
4. **The platform stays key-less.** This track adds nothing to the platform's key exposure — `grant-keyd` keeps minting-wrapping-dropping. Reaffirmed as an invariant, CI-guarded.
5. **Continuous/automatic forward secrecy (MLS/TreeKEM) is a reserved premium.** For the narrowest, highest-assurance streams only; it carries a substantial build and the brokerless commit-ordering problem, and it is **not** the baseline. Deferred to a later, reviewer-gated ADR — the SDK's KeyPackage-shaped seams (ADR 1094 §8) keep the door open, but nothing MLS is claimed as built.
6. **Compliance policy is the backstop, not the pitch.** The SDK's default practices can later be encoded as coalition/NATO data-handling policy — e.g., a required rotation cadence, and post-receipt handling rules (received data, *even when unclassified*, not exposed on an endpoint merely reachable from the public internet). Adoption is won first on the tool's quality; policy makes the good habit mandatory once it is already the norm. Keep it proportionate — usefulness before mandate.

## Alternatives considered

- **`goat-cli`-first (a single CLI/surface).** Rejected: not good enough for a large community building heavy-duty systems; a single surface/language can't be the substrate others build on. `goat-cli` is a valued *consumer* of the SDK instead.
- **Python (or any single-language) SDK.** Rejected: Python is right for fast, readable teaching (`grant_enc.py` stays as exactly that), wrong as the production substrate for a multi-language sovereign community. The usual suspects must all be first-class.
- **Try to *force* forward secrecy by owning the client.** Impossible and mis-framed: we do not own the sovereign receiver's endpoint. Signal's owned-app model does not transfer; the honest lever is adoption + defaults + policy.
- **Build MLS/TreeKEM now as the baseline.** Rejected: a premium most systems lack, heavy, with an unsolved brokerless-ordering piece; unnecessary given need-to-know is already maximal and the residual is closed by destructive rotation.
- **Do nothing — leave the reference libraries.** Rejected: reference libs can neither *default* to nor *enforce* good hygiene, so forward secrecy stays a memo nobody adopts. The whole point is a tool so good the secure default rides in for free.

## Consequences

- A real, ongoing **SDK program** — a multi-binding surface to build and maintain. The `WIRE-FORMAT.md` spec + conformance vectors (already built) are the load-bearing contract that keeps every binding honest; the C ABI is the single choke point that keeps the count of real implementations at **one**.
- **Forward secrecy becomes the path of least resistance.** A sovereign using the SDK as shipped gets ephemeral keys + destructive rotation by default; the endpoint residual is minimized without the sovereign having to be an expert.
- **Security-by-adoption, then by policy.** Sovereigns choose the tool because it is excellent; coalition policy can later require the practices it already defaults to — the reverse of shipping a mandate no one wants.
- **One audited implementation** under every consumer (goat-cli, portal, partners) — no drift, one place to review, one place to harden for FIPS/PQC.
- The platform's **key-less** property is unchanged and made an explicit invariant.

## How this track is run

Executed by **delegated teams of agents with clear roles** — implementers, a **supervisor** per work-stream, independent **critics** (adversarial design/security review), and **code reviewers** — not a single pass. **The ceremony is tiered (critic pass):** the full adversarial/supervisor/critic apparatus applies to the **core + C ABI + wire format/vectors** (the security-critical, audit-once surface); bindings and packaging get ordinary code review + the conformance gate. Nothing merges without a reviewer + the conformance-vector gate. **After the track is otherwise complete, the entire SDK goes through a final whole-system review, refactor, and improvement pass** (one more adversarial read for coherence, misuse-resistance, and simplification) before any release is cut. Simplicity and clarity are review criteria, not afterthoughts. The Phase-0 critic pass ran 2026-08-01 (3 independent critics); resolutions are folded into the survey doc and this ADR.

## Build plan / work track

**Phase 0 — Prior-art survey, spine & API (immediate).**
- **Survey the field and decide what to reuse.** A deliberate review of best-in-class crypto/SDK work, each assessed for *approach to steal* and *code to vendor* (license-permitting). Candidates to study: **Google Tink** (Apache-2.0 — the closest analog: multi-language, safe-by-default, key management), **libsodium** (ISC — the gold standard for misuse-resistant API design), **age/rage** (permissive — superb envelope/recipient UX), **RustCrypto** + **aws-lc-rs** (vetted primitives / FIPS, already in-stack), **Mozilla UniFFI** / **cbindgen** / **wasm-bindgen** (binding generation — note MPL-2.0 tooling is usable to *generate* glue, held to a different bar than *vendored* product code), **OpenMLS** (MIT — for the reserved MLS tier). Output: an adopt/adapt/build decision per component, with licenses verified (permissive-only for vendored code; faithful attribution).
- **Freeze the public API** from the existing core: `seal`/`open` (envelope), `admit`/`open` (consumer key store), and a first-class **`rotate --destroy`** with **ephemeral-by-default** key handling. Adopt `WIRE-FORMAT.md` + conformance vectors as the SDK's conformance gate. Pick the canonical SDK repo home (a `usareur-af` sibling, per the hello-galaxy pattern).

**Phase 1 — Harden the Rust core as *the* SDK.** Wire zeroization of DEKs and retired keys (with the honestly-stated ceiling — move copies, AEAD key-schedule copies, no mlock by default); ephemeral-by-default persistence policy; destructive-rotation default (no re-wrap) + member-side `--keep-access` opt-out; enforced message-count rotation cap; build matrix Linux/macOS × x86-64/arm64 (Windows demand-gated); **FIPS as a build feature, not a Phase-1 gate** — FIPS mode re-bases the primitive stack from RustCrypto onto `aws-lc-rs`/`aws-lc-fips-sys` (a real re-base + conformance re-run, not a flag; pin the pair, verify by compiling — F-260). **Per-suite FIPS honesty: v1 (`v1-ecdh-p256`) is FIPS-capable; v2 (X-Wing hybrid) is beyond-FIPS defense-in-depth and can never be a FIPS-mode tier.** The stable **C ABI** surface (fail-closed handle lifecycle: poisoned post-dispose, explicit-dispose-only, error mapping preserving the capability-vs-reject distinction). Ship with docs + quickstart + tests to a premium bar.

**Phase 2 — Committed bindings: Go, Python, TS/JS** (the named consumers), thin hand-written wrappers over the C ABI, published in lockstep from one core tag. Each binding gates on the decrypt-direction conformance vectors + write-side RNG-injection tests before release. Further languages/platforms are demand-gated (see Decision §1).

**Phase 3 — Consumers & polish.** `goat-cli` re-based on the SDK; per-language quickstarts and example integrations; the "so good they adopt it" documentation and DX. Retire ad-hoc reference paths in favor of the SDK (keep `grant_enc.py` as an explicitly-labeled teaching reference only).

**Phase 4 — Reserved premium (gated).** MLS/TreeKEM continuous forward secrecy for the highest-assurance tier, including the brokerless commit-ordering design; separate reviewer-gated ADR; not a blocker for Phases 0–3.

**Parallel — Policy backstop.** Draft the coalition/NATO data-handling practices the SDK defaults to (rotation cadence; post-receipt handling). Non-blocking; usefulness leads, mandate follows.
