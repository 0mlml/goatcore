## TL;DR (for a layperson)

We built the machinery that encrypts data to only the people allowed to read it (ADR 1094). This decision settles *who decides* and *whose keys are used*, so a real data owner — not a platform admin — can drive it. An **organization** owns the decision to share its data; a person in that org, acting as its **data-governance admin**, makes the grant. The owner has full say over what it releases — the platform records the decision (an audit trail) rather than blocking it. Every individual and machine holds **its own** key; the organization is just how we group and address them, never a shared password. And the list of who-gets-a-key is **computed** from the grants and the org roster on demand, never a hand-kept list that can drift.

## Context

ADR 1094 built grant-keyed encryption but left the identity model implicit: what a "member" of a release-set is, who may grant, and whether keys are per-person or per-org. Making the capability usable by a data owner (not a platform admin) forced those questions. Three facts from the code shaped the answers: the fabric's real machine-identity axis is the cert **CN/write-anchor**, not the URI-SAN (the router ACL matches CN; a SPIFFE SVID composes by CN); the **roster keys members by email-hash/handle/producer-anchor**, not by any SVID path, so an org→member-key mapping must be *derived*, not read from one field; and onboarding's `certmint` already issues each holder a **per-holder EC leaf keypair** (the enrollment key the design says you unwrap with).

## Decision

**Organizations own the sharing decision; individuals and machines are the actors and key-holders; the audience is a derived projection of the identity graph; keys are per-individual.**

1. **Authority is organizational, expressed as a role.** An org owns its data's sharing decision. The authority is **`data.govern.org:<O>`** — a sentence in the closed data-access role grammar (ADR 1074), derived from the nomination store by construction, generalizing the per-producer custody gate to the org. **Canonical model:** governance is held only by an org's **nominated** admins (`govern_admins` rows), and a **new org is seeded with its first member** as its initial admin so it is never born locked out; the platform team establishes admins at onboarding and the org's owners modify them afterward (onboarding mints identity; governance sets access — kept as separate concerns). **Kick-start default (current):** a per-goatnet flag `GovernBootstrapOpen` (env `PORTAL_GOVERN_BOOTSTRAP_OPEN`, default `true`) makes the goatnet start **open** — any member of an org that has not yet nominated anyone may govern it, and orgs narrow themselves to named admins as they mature. It is a deliberate, explicit starting posture, **not** a structural assumption: an org WITH nominations is always governed only by its nominees, and setting the flag `false` gives the canonical fail-closed model with no code change. Governance is **single-sourced** — computed once in `Server.governedOrgs` from the nomination store + the flag, never emitted by the pure roster resolver — so the resolver surface and the grant/govern gates read one definition. **Proxy stewardship:** a platform operator may be *explicitly* granted `data.govern.org:Y` — audited, time-boxed — to act for a sovereign not yet operating its own admins. The at-most-own-scope nomination surface is the ADR 1071/1072 sponsor pattern.

2. **Owner authority is audit-accountable, not system-gated.** A producer defines whatever release-set it chooses: holding the data confers the authority to release it. Coalition/release-lane eligibility (ADR 1077) is **advisory context, never a hard gate** on a grant — consistent with the standing principle that over-restriction of unclassified releasable data is usually a mislabeling. Every grant/revoke is an audited action; the platform records the decision, it does not second-guess it.

3. **Keys are per-individual; the org is the grouping/addressing unit — not a shared key.** A single org keypair copied to members was rejected: it forces a whole-org re-key to remove one person (a shared key can't exclude one holder), makes the private key a distributed secret with no per-member attribution, and fights the per-workload SVID model. Each individual and machine holds its **own** enrollment-cert keypair. Two tiers of human: a **cert-holding client** (a person running a client / a workload) decrypts with its own key; a **browser-only** human holds no wrapping key and reads through the human-plane surface (a mediated read). Scale-relief past a comfortable flat audience is the **key tree (MLS/TreeKEM)** — never a static shared key.

4. **The audience is a derived projection, never a stored list.** "Grantee org Y's key-holders" is read from the identity relationship graph (a cert is *anchored at K*; membership is a typed edge — ADR 1051/1065, a read-only projection never in an enforcement path). Served by `GET /api/access/audience?release_set=<K>`: it expands K's in-effect grant rows (org grantees → the producer anchors under them; principal grantees → their machine anchor, or a note if browser-only) and always includes the producer itself (producer-as-member DEK handoff). Resolved to keys through an **org-indexed member-key directory** (operator-provisioned cert dir at launch; the durable F-267 fabric directory later).

5. **Naming: the member id is the write-anchor/CN.** The bundle slot key and the key-source lookup key are the fabric's real machine-identity axis. Affiliation (nation / coalition) is identity-only, deliberately never the write anchor (ADR 1043) — it informs *who* an owner shares to (the org graph: a unit under another nation's command shares from its own ownership to that formation), never the wrap key. **A release-set = one producer anchor** (`rs ≡ producer`) for the MVP.

## Alternatives considered

- **A shared per-org key (individuals hold copies).** Rejected — decision 3: no granular revocation, a distributed secret, no attribution. The properly-done version of this idea is MLS/TreeKEM (the named scale path), not a static shared key.
- **A central releasability gate on grants** (coalition standing hard-blocks a grantee). Rejected — decision 2: the owner is the authority; accountability is the audit trail. Standing stays advisory.
- **A stored org→member-key table.** Rejected — decision 4: the mapping is latent in identity (cert anchor + membership edge); a maintained table drifts and violates the virtual-role discipline (ADR 1074).
- **A bespoke governance-role system beside the grammar.** Rejected — decision 1: `data.govern.org` is one more virtual sentence in the existing enforced grammar; no parallel machinery.

## Consequences

- The capability becomes **data-owner-driven**: the existing `goat access grant` (its custodian gate is the bootstrapped `data.govern.org` for the common single-producer case) now sets a real encryption audience via the derived endpoint.
- **Built (this ADR's scope):** the producer/consumer data path (Piece A, ADR 1094 implementation), the `GET /api/access/audience` endpoint + the `GrantRowAudienceResolver` (Piece B). **Piece C built 2026-07-31 (portal-minted plane):** the portal persists each minted public leaf to a by-anchor recipient-cert store served at `GET /api/access/recipient-cert`; grant-keyd syncs + re-validates it into its cert dir (F-267 residual closed for that plane; the v2 hybrid KeyPackage directory remains staged). **Piece D built:** the `data.govern.org` grammar sentence + retroactive bootstrap landed 2026-07-30 (#1923); nomination/removal landed 2026-07-31 — `govern_admins` registry rows + `POST /api/access/govern-admins[/{id}/remove]`, at-most-own-scope gate, monotonic narrowing (an org with active nominations confers the role only on its nominated admins, on both planes; last-admin removal refused). **Single-sourced + config-gated 2026-08-01:** governance authority moved out of the pure roster resolver into one place (`Server.governedOrgs`), computed from the nomination store + the per-goatnet `GovernBootstrapOpen` default; the "any member governs a not-yet-nominated org" behavior is now the explicit open default (true today), and `false` is the canonical fail-closed model. Fail-closed is the safe struct zero-value. **Cutover built 2026-08-01:** the portal self-triggers the migration when a goatnet is set fail-closed (`internal/api/govern_seed.go`, `RunGovernReconcile`, wired before the HTTP listener so no request is served against an unseeded org). Two mechanisms, both bridging the roster's per-org email-hashes to identity UUIDs via one Kratos scan: **(a)** a one-time existing-orgs migration nominates **every** current person member of every not-yet-narrowed org — behavior-preserving (they all governed under the open default), **not** retroactive-first-member (existing orgs keep all members), guarded by a `govern_meta` marker so it runs once; **(b)** a going-forward first-member reconcile seeds the **first** resolvable member of any new zero-admin org (re-checked on `PORTAL_GOVERN_RECONCILE_INTERVAL`, default 5m, so a freshly onboarded org is governed without a restart). Machines are never seeded (nomination is person-keyed); an org whose members have no matching identity is logged and recovered via proxy stewardship. The ZAGROS flip rides the deploy that bumps the portal pin to an image carrying this code (flag + binary atomic — a fail-closed flip on an old image would lock out every org). **Still future:** the platform-team-establishes-at-onboarding wiring (governance set at onboarding, modifiable by org owners) — the going-forward auto-seed makes the first onboardee the initial admin; explicit onboarding-time nomination by the platform team is the next increment.
- **New onboarding obligation:** every individual data-actor needs a per-holder decrypt keypair. `certmint` already issues one; Piece D confirms it reaches every intended individual, not only machines/participants.
- Live end-to-end validation on a goatnet is gated on standing grant rows + the key service pointed at the portal (a deploy/operator step), not on further code.
