# ADR 1063 — goat-client connectivity check + peer file drop: Tailscale-parity features on the inner mesh

**Status:** Proposed. Designed-not-built. Design: [`goat-client-connectivity-and-filedrop.md`](../design/goat-client-connectivity-and-filedrop.md).
**Repo scope:** **v1 is goat-client-only.** All of Feature 1 + Feature 2 v1 land in `goat-maintainer/goat-client` (daemon + GUI: a new `internal/peerping/` prober, a new `internal/filedrop/` HTTP server, an `internal/innermesh` status-read extension, two new IPC methods, and a Fyne device-roster + detail pane); goat-core carries only this design doc + ADR. **Phase 2 (offline store-and-forward) is the single piece that touches core** — it modifies the Rust relay crates (`goat-relay` / `goat-relay-protocol`, top-level in this repo). v1 basic transfer needs none of it: the relay carries the encrypted tunnel transparently, so direct + relay-fallback drop is 100% goat-client.
**Related:** [`goat-client.md`](../design/goat-client.md) ([ADR 0840](0840-goat-client-cross-platform-daemon-gui.md)) (the daemon + GUI this extends) · [ADR 0709](0709-block-33-relay-rewrite-architecture.md) (the Rust relay — throughput + the offline store-and-forward lever) · ADR 1043 (identity-grade authz) · F-207 (audit trail) · [ADR 1032](1032-zenoh-volatile-non-persisted-namespace-class.md) (`volatile/blob` — the adjacent-but-different transfer layer)

## Plain-language summary

Tailscale's app shows a live per-device **connectivity check** (a latency graph + a "Direct vs Relayed" badge) and **Taildrop** (drag-a-file peer-to-peer). NetBird provides neither, and goat-client does not yet. This ADR adopts building both into goat-client as **inner-mesh peer features**, because we already own every hard primitive: a stable per-peer overlay IP, source-IP-as-identity authentication, NetBird linked as a library inside the daemon, and our own Rust relay. We reach **functional parity** on both, **exceed** Tailscale on relay-path throughput / offline store-and-forward / identity-grade authz / audit / sovereignty, and accept one ceiling we cannot match: NetBird's coarser NAT-traversal plus a small relay footprint means our path badge will read "Relayed" in some adversarial-NAT cases where Tailscale would have gone direct — a ceiling a deliberately small site scope largely retires.

## Context

- The Tailscale macOS app's per-device pane is the state of the art for "feels like a finished mesh client": a rolling latency line, a direct/relayed badge, and a Taildrop drop zone. Stock NetBird has none of it; the upstream "Send File" ask (#2132) is unshipped.
- goat-client (ADR 0840) is a cross-platform daemon + Fyne GUI that already links NetBird as a library (`internal/innermesh/`) in `netbird-only`/`combined` modes. So peer status is readable in-process, and the GUI is the natural home for the UX.
- **Inner mechanism, verified from Tailscale source/docs:** the Ping panel is *two* data sources — a latency number from **repeated disco pings** (an app-layer-equivalent echo; transport-level only for Tailscale's own reasons) and a path badge from **transport path knowledge** (which an app-layer echo cannot see, because WireGuard hides the underlay). Taildrop is an **HTTP `PUT` server bound to the tunnel IP**, authenticated by `WhoIs(source-tunnel-IP)` — the mesh's source-IP authentication *is* the identity.
- **What NetBird gives free (verified from the fork):** `netbird status --json` already carries `connectionType` (P2P/Relayed), `iceCandidateType`, `relayAddress`, live handshake, and byte counters — the path badge is a *read*. **What it does not:** a usable live latency (its `latency` is a one-shot frozen at ICE-pair selection, absent on the relay path), and any file transfer (none).
- **Scope reality:** the wg-cp0 outer tunnel is single-peer, so both features are inner-mesh-only — live in `netbird-only`/`combined`, dormant in `wg-cp0-only`. This nudges goat-client.md §2's "mesh-service-level UX out of scope": peer ping/drop is *mesh-peer* UX (post-v1 here), not *mesh-service* UX (still out).

## Decision

1. **Build both features into goat-client as inner-mesh peer capabilities** — live in `netbird-only`/`combined`, dormant (empty device list) in `wg-cp0-only`. Additive on the inner-mesh side; the wg-cp0 outer tunnel is untouched.
2. **Connectivity check = our latency + NetBird's path.** A new `internal/peerping/` runs a UDP-echo responder bound to the inner-mesh tunnel IP and a monotonic-clock sender keeping a per-peer RTT ring buffer (this fills NetBird's missing live latency; both ends run goat-client). The direct/relayed badge is *read* from the in-process NetBird status (`connectionType`/`iceCandidateType`/`relayAddress`), never inferred from the echo. The existing `internal/reachability/` prober (wg-cp0 relay dial-selection) is **not** reused — different target, different semantics.
3. **File drop = an HTTP server on the tunnel IP, mesh-authenticated.** A new `internal/filedrop/` serves `PUT /put/<name>` bound to the inner-mesh tunnel IP (mesh-only, never public), streaming to an inbox dir, with identity = the connection's source overlay IP resolved against the NetBird peer list (the `WhoIs` analog). A `goat send <peer> <file>` CLI + a GUI drop zone PUT to `<peer-tunnel-ip>:<port>/put/<name>`. No separate auth token — the mesh already enforces source-IP identity.
4. **Two new IPC methods + a shared device-roster/detail UI.** `getPeerConnectivity(peer)` and the filedrop send/status calls extend the existing JSON-RPC surface; the Fyne GUI gains a device roster + per-peer detail pane (the roster is shared infrastructure for both features and the largest single UI chunk).
5. **Sequence: fast-validate, then Feature 1, then Feature 2 v1, then the relay store-and-forward differentiator.** A throwaway echo + one-file PUT between two peers proves the mechanics before the UI build. Direct + automatic relay-fallback transfer is v1; relay-side store-and-forward to *offline* peers is phase 2 (the one piece that touches the Rust relay).
6. **Honest parity expectations are part of the decision.** We adopt the build knowing (a) one ceiling we cannot match — NAT-traversal hit-rate + a small relay footprint means the path badge reads "Relayed" in some adversarial-NAT cases Tailscale would win, retired largely by a small site scope; and (b) the exceed set — relay throughput (ADR 0709), offline store-and-forward, identity-grade authz, evidence-grade audit, and sovereign/denied-environment operation — which is what justifies building these natively rather than deferring to scp.

## Alternatives considered

- **Tell users to scp/sftp over the mesh — rejected.** It is NetBird's own guidance and it works, but it is not a one-click drop and forfeits the identity-attribution, audit, and offline store-and-forward we can offer. The whole point is the finished-client UX.
- **Reuse `internal/reachability/` for the peer latency — rejected.** It probes wg-cp0 relay endpoints for dial-selection and deliberately discards RTT jitter. A live peer graph is the opposite contract (it *wants* the jitter, on a different target). A separate `internal/peerping/` is correct.
- **Replicate Tailscale's disco for the path badge — unnecessary.** NetBird's status already exposes P2P-vs-Relayed + ICE candidate type. We read it rather than re-implement a transport-level discovery protocol. (If NetBird ever stopped exposing connection type, racing a control-ping across candidate endpoints would be the fallback — noted, not built.)
- **Route file drop through the Zenoh `volatile/blob` class — rejected for this surface.** `volatile/blob` (ADR 1032) is fabric-mediated bulk transfer for services on the Zenoh bus; goatdrop is direct HTTP peer-to-peer over the WG tunnel for laptop/phone users. Different layer, different users — kept separate by design.
- **Add a separate per-transfer auth token — rejected.** Redundant with the mesh's source-IP authentication, and the thing most likely to rot. Trust the tunnel.
- **Ship the relay store-and-forward in v1 — deferred to phase 2.** It is the one feature needing relay customization; basic transfer rides the relay transparently already. Sequencing it second keeps v1 small and gets at-parity drop out first.

## Consequences

- goat-client reaches functional parity with Tailscale's two headline per-device features, with a relay path that is faster than DERP and an identity/audit/sovereignty posture Tailscale structurally lacks.
- The device-roster + detail pane is new shared UI that both features (and any future per-peer affordance) build on.
- One acknowledged ceiling: the direct/relayed badge will read "Relayed" more often than Tailscale in adversarial NAT, inherited from NetBird's ICE + our relay footprint, not from our UI — bounded by a small site scope.
- The phase-2 relay store-and-forward is a known, scoped extension that touches the Rust relay; basic transfer does not.
- Designed-not-built; the build lands in `goat-maintainer/goat-client` with its own release + (eventual) live-fire, not in goat core.
