## TL;DR (for a layperson)

The most important parts of the system — the management plane
components we wrote ourselves or had to patch — are built from
source by our own pipeline. We don't pull a pre-built binary
or image from anyone else. This is the strongest supply-chain
posture: every line of code is reviewable, every build is
reproducible, every artifact is signed by us.

## Context

Three categories of management-plane software:

1. **Bespoke** (we wrote them): signal-server, gatewatch,
   ntp-health-agent, ntp-admit-sidecar, admit-audit, db-policy-engine.
   Always built from source by our pipeline.
2. **Patched upstream** (we modified them): netbird-management
   ([`0301`](0301-patched-netbird-management-image.md)),
   postgres-spock. Built from source via our patched fork.
3. **Stock upstream**: Chainguard images
   ([`0700`](0700-chainguard-first.md)) where available.

Categories (1) and (2) belong in our own build pipeline.
Category (3) consumes Chainguard.

## Decision

Build-from-source applies to all bespoke and patched mgmt-plane
components:

- **Bespoke services**: built in our CI from in-repo source.
- **Patched upstreams**: forked, in-repo, built in our CI.
- **Multi-arch**: amd64 + arm64 native builds (no QEMU in CI;
  per-arch native runners).
- **Pin tools**: Go toolchain pinned via `GOTOOLCHAIN=auto`
  for upstream-version compatibility; Rust toolchain pinned
  in `rust-toolchain` ([`0707`](0707-rust-toolchain-pinning.md)).
- **Output**: GHCR-published, cosign-signed, pinned by digest
  in compose files.
- **Pin regression guard** ([`0703`](0703-pinned-digests-and-pin-regression-ci.md))
  prevents accidental tag drift.

Specific component build pipelines:

- **netbird-management**: `ops/netbird/`, GitHub Actions.
- **postgres-spock**: own image build with bake-in pgBackRest.
- **signal-server**: in-repo Dockerfile + Go modules.
- **All Go services**: govulncheck in CI
  (`0704`).
- **Rust components**: cargo-audit + clippy in CI.

## Alternatives considered

- **Consume upstream images entirely.** Loses end-to-end
  attestation. Rejected for bespoke / patched.
- **Build only "critical" components from source.** Hard to
  draw the line; produces inconsistent posture. Rejected.
- **Outsource builds to a partner pipeline.** Adds prime-
  capture risk ([`0104`](0104-no-prime-capture.md)). Rejected.

## Consequences

**Positive.** End-to-end provenance for management plane.
SBOM is generated by our pipeline (we know exactly what's in
each image). Signed by us; pinned by us.

**Negative.** CI maintenance burden. We accept; this is
where the supply-chain posture earns its keep.

## Assessor view (SCA-R)

Build-from-source serves SR-3 (supply chain controls), SR-4
(provenance), SI-7 (software, firmware, integrity), CM-3
(change control — every build is a tracked CI run), and
SA-12 (supply chain protection).

## Trigger conditions for revisit

- An upstream becomes too divergent to maintain a fork.
  Negotiate upstream PR landing or rewrite.
- A specific component is too small to justify build cost
  and Chainguard ships an equivalent. Move to Chainguard.
