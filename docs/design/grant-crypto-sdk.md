# grant-crypto SDK — frozen Phase-1 public API

The canonical design for the grant-crypto SDK ([ADR 1106](../adr/1106-grant-crypto-sdk-and-endpoint-forward-secrecy.md)): one Rust core behind a hand-authored versioned C ABI, thin hand-written bindings (Go / Python / TS), secure-by-default forward-secrecy hygiene. This doc **freezes the v1 public surface** — the verbs, their contracts, and the invariants — so every binding is the same library. Inputs: the Phase-0 prior-art survey + critic pass and the normative wire spec [`ops/grant-crypto/WIRE-FORMAT.md`](../../ops/grant-crypto/WIRE-FORMAT.md). The exact Rust signatures and the C header are authored against this doc and reviewed against it; where they conflict, this doc wins until amended by PR.

**Repo home (interim, ADR 1106 open-item 3):** `ops/grant-crypto/sdk/` — a self-contained Cargo workspace (no path-deps outside the subtree) so the later split to a sibling repo is a directory move. `grant-keyd` and other goat integrations consume the SDK from outside the subtree; nothing inside it knows about Zenoh, the portal, SPIRE, or ZAGROS.

**Reference convenience consumer:** `goat-cli` (`goat-cli.md`). It holds no crypto of its own — `goat pub --sealed` / `goat sub --open` delegate to `grant_crypto::datapath`, and `goat access key rotate` to `grant_crypto::rotate::rotate` — depending on `grant-keyd` only for the SPIRE-SVID bundle-signer verification the SDK core deliberately excludes. This is the ADR-1106 realization that **goat-cli leverages the SDK as a convenience path, not the only path**: the operator gets one binary, and the identical SDK stays directly usable from Rust/Go/Python/C. It is the worked example the bindings and other consumers can read.

## Invariants (load-bearing; CI-guarded where possible)

1. **The platform holds no keys.** The key service mints a DEK, wraps it to each authorized member, publishes the bundle, drops the DEK. The service API exposes **no function that returns plaintext or a DEK**.
2. **Only members decrypt, in-process.** The consumer returns plaintext only to the holder of the member identity key. A non-member has no slot; `admit` fails closed.
3. **The producer is not a key authority.** `seal` takes **no recipients** — a producer seals under a stream key it unwrapped from its *own* bundle slot. Only the key service resolves an audience and wraps.
4. **Forward secrecy is endpoint-enforced.** Default rotation destroys the retired private key with **no re-wrap of anything**; losing pre-rotation re-fetch *is* the forward secrecy. The platform can never re-wrap (it holds nothing to re-wrap).
5. **Suite-agnostic by construction (PQC-ready).** No algorithm, nonce, or RNG appears in any public signature. The suite id travels in the data and is AAD-bound (WIRE-FORMAT). `Recipient`/`Identity` carry suite-typed key material — v1 P-256 today, the hybrid X25519+ML-KEM shape (`v2-x25519-mlkem768`, inert) without an API break. Shipping any new suite is a separate, audit-gated decision; *accommodating* it is not.
6. **Fail closed, quietly.** Unknown suite → `UnsupportedSuite` before any key operation. Missing slot → `NoSlot`. Every other failure is a reject; error variants are advisory, never an oracle.

## The frozen v1 surface (language-neutral)

Five nouns, six verbs, plus two write-side verbs and their two value types added 2026-09-07 for F-498 — recorded here rather than absorbed silently, because this surface is frozen. Both additions are **additive**: no existing signature changed, no wire format changed, and nothing a consumer calls behaves differently. Names below are the canonical vocabulary; each binding renders them idiomatically (`key_store.open()` in Python, `keystore.Open()` in Go) but adds, removes, or reinterprets nothing.

**Nouns**
- **`Identity`** — a member's id + private key material (suite-typed). Unwrap-capable. Never serializable with key material in the clear; constructed from the member's enrollment credential.
- **`Recipient`** — a member's id + public key material (suite-typed). Wrap-capable only. Realized today service-side as `service::Member` (the audience entry the key service wraps to); it is deliberately **not** on the consumer/producer binding surface — bindings never wrap.
- **`Context`** — the required typed AAD binding: today the data topic (key expression). Mandatory on seal and open; there is no context-free overload.
- **`KeyBundle` / `Envelope`** — the wire structures, exactly per WIRE-FORMAT.md (parse/serialize helpers included; construction only via the verbs).
- **`AudienceExpectation` / `AudienceConfirmation`** *(added 2026-09-07)* — the input and output of `confirm_audience`. The expectation is stated as member **ids** to include and exclude, never a count: a count cannot distinguish "the member I removed is gone" from "somebody else left in the same window". Neither goes on the wire.

**Verbs**
- **`verify(bundle, trust) -> ()`** — authenticate a bundle against the key-service verifying key (or its carried SVID against a trust root). Consumers MUST verify before admit; the convenience path does it for them.
- **`admit(keystore, bundle, identity) -> had_slot`** — unwrap this member's slot (if any) and retain the DEK for `(rs, gen)`. `false` (no slot) is a normal outcome, not an error; fails closed on malformed slots.
- **`open(keystore, context, envelope) -> plaintext`** — open a data message with the held DEK for its `(rs, gen)`; `NoSlot` if none held. The consumer order `verify → slot → unwrap → open` (WIRE-FORMAT §Conformance) is enforced by construction, not by caller discipline.
- **`acquire(bundles, rs, identity) -> StreamKey`** — the producer's path to a seal-capable key: pick the highest generation of `rs` with a slot for this identity, unwrap it. `NoSlot` if the producer isn't in the audience.
- **`seal(stream_key, context, plaintext) -> Envelope`** — one-shot seal under the acquired key. No nonce, no algorithm, no RNG parameter — the implementation supplies a fresh random nonce internally and stamps `(suite, rs, gen)`.
- **`seal_current(stream_key, context, plaintext, bundles) -> Envelope`** *(added 2026-09-07)* — seal only while this key's generation is still the newest visible for its release set; `Superseded` otherwise. `seal` alone cannot notice that the owner narrowed the audience, so a member removed from a release set keeps reading everything published afterwards. Judged by **generation, not membership**, so a producer dropped from its own audience still learns it was superseded. The bare `seal` is unchanged, which is why this is a separate verb and not a behaviour change.
- **`confirm_audience(rs, bundles, expectation) -> AudienceConfirmation`** *(added 2026-09-07)* — read the published bundle **back** and check who holds a slot in its newest generation; `AudienceNotApplied` when a member that should have lost one still has it, or one that should have gained one has not. Exists because a publish returning success proves only that a write was attempted — silent denial is this fabric's standing failure mode — and because the operator's ruling of 2026-09-07 is that a publisher which changes access must **validate** the change took effect rather than infer it from the absence of an error. Fail-closed when no bundle is visible: seeing nothing is not seeing the change applied.
- **`rotate(identity, policy) -> RotationReceipt`** — the member-leaf rotation hygiene (composes with ADR 1044 re-issue): `Destroy` (default) zeroizes the retired private key, no re-wrap; `KeepAccess` first re-wraps this member's *own held* still-live DEKs to the new key, locally, then zeroizes — labeled as reducing FS. The receipt is a **structured, self-dating fact** (retired key id, count of now-unreadable pre-rotation generations, timestamp), never time-relative prose.

**Key service (the other side, same crate, disjoint types):** `mint_and_wrap(audience, rs) -> KeyBundle` + `sign` — today's `KeyService::rotate` pipeline (resolve → mint → wrap-to-each → sign → publish → drop). Structurally incapable of returning a DEK; the enforced **message-count rotation cap** (below) lives here.

**Secure defaults (not options):** DEKs are fetched-unwrapped-used ephemerally; nothing persists key material unless the caller explicitly builds persistence; `rotate` defaults to `Destroy`; the seal path enforces a **cumulative message-count cap** per `(rs, gen)` with margin below the GCM birthday bound — at the cap, seal refuses until rotation, and the approach is surfaced (`remaining()`) well before refusal. The counter is **cumulative within the process** — re-acquiring the same generation carries the count forward, so the natural "hit the cap, re-acquire, continue" path cannot silently reset the nonce budget on an unchanged DEK; across processes/restarts the systemic guarantee is the key service publishing new generations (rotation re-keys). The cap is **monotone tighten-only**: a later `set_cap` can lower it, never raise it back.

**Explicitly NOT in v1** (each returns/raises cleanly, none half-exists): streaming/chunked construction (future suite id + own design pass), history backfill (declined, ADR 1106), MLS/CFS tier (reserved, own ADR), WASM (deferred; never key custody), any API that hands the platform a DEK.

## Error taxonomy (frozen, all bindings)

Nine variants. The six of the original core, verbatim: `UnsupportedSuite` (capability signal, pre-key), `BadSignature`, `NoSlot`, `Unwrap`, `Decrypt`, `Malformed` — plus `RotationRequired`, added in the Phase-1 hardening to carry the enforced message-count cap below (Secure defaults). `RotationRequired` is the **write-side local refusal** `seal` returns at the cap: it is distinct from `Decrypt` (never a decrypt oracle), and it changes nothing on the wire — no conformance vector observes it — so it does not touch the frozen wire format or the read-direction taxonomy. Beyond this one additive variant (required by the cap this doc already mandates), no binding adds variants or collapses two, and every binding preserves the capability-vs-reject distinction. Two further additive variants landed 2026-09-07 for F-498, both **write-side local refusals** of exactly the same character as `RotationRequired` — never a decrypt oracle, nothing on the wire, no conformance vector observes either: **`Superseded`** (the held generation is no longer the newest, so sealing under it would keep publishing to a superseded audience) and **`AudienceNotApplied`** (a change read back off the fabric has not taken effect). C ABI: negative `int32` codes, stable forever (`RotationRequired = -7`, `Superseded = -8`, `AudienceNotApplied = -9`); `0` = success.

## C ABI contract (Tier 1 — the audited seam)

- Crate `grant-crypto-capi` → `cdylib` + `staticlib`; header generated by cbindgen, committed, reviewed as source. Prefix `gc_`. `gc_abi_version()` returns a monotone integer; **no cross-version ABI promise** — core + wrappers ship in lockstep from one tag (SONAME-pinned).
- **Opaque handles only.** Key material never crosses the boundary as bytes into a managed heap. Wire structures (bundle/envelope JSON) cross as bytes; keys never.
- **Fail-closed handle lifecycle:** handles are generation-tagged/poisoned — any use after `gc_*_dispose` returns an error (never dereferences freed state); double-dispose is a harmless error; a handle is single-thread-or-caller-synchronized by contract. **Explicit dispose is the only sanctioned release path**; a GC finalizer in a binding may report a leak, never dispose (a binding MAY additionally expose report-only leak diagnostics, e.g. a leak counter — diagnostics, not lifecycle). Dispose zeroizes, best-effort, with this **stated ceiling**: Rust move semantics leave stack copies; `[u8; 32]` by-value returns at the conformance layer copy; the AES key schedule expands round keys the zeroize story never touches; plaintext and receipts copied into a managed language are that caller's to manage; no mlock/guarded allocation (a possible later opt-in, never a silent promise). Within that ceiling: identity scalars, held DEKs, stream-key DEKs, and buffer contents are wiped on dispose/drop, and local key copies are wiped after use.
- Out-params + status-code returns throughout; no errno, no thread-local last-error required for correctness (a `gc_error_message(code)` static-string helper exists for diagnostics only).

## Conformance gate (what "one implementation" means, honestly)

- **Read side:** the shared decrypt-direction vectors (today `ops/grant-crypto/envelope/testdata/vectors/`) are a required CI merge gate for the core and every binding — byte-for-byte accept/reject parity, including the negative cases (wrong key/gen/rs/topic, tamper, unknown suite, bad signature). No vector pins ECDSA `sig` bytes (signing is nondeterministic across backends); vectors verify signatures.
- **Write side (vectors can't cover it — the write path is deliberately nondeterministic):** every binding's suite seals through the binding and re-opens the result (write-read roundtrip incl. wrong-topic fail-closed), and asserts **nonce freshness on sealed output** (repeated seals of the same plaintext produce distinct nonces). Two strengthenings are queued follow-ups, not yet built (stated so the claim can't outrun the tests): a deterministic-RNG injection seam in the core for true uniqueness assertions, and a binding-sealed → Go-reference-opened cross-implementation leg (today the Go-sealed → Rust-opened direction is covered by the vectors themselves). The AAD binds suite + both keys, and the wrong-topic/tamper negatives in every suite prove the fail-closed behavior.
- A binding that fails either gate does not ship. Vectors prove read-interop; RNG-injection proves write safety; neither claim borrows the other's coverage.
- **Reject-class latitude (one case, stated so it can't creep):** the accept/reject *decision* (+ plaintext on accept) is the binding contract; a vector's `reason` string is advisory. One structural divergence is expected and allowed: a wrong-generation envelope rejects as `Decrypt`/open-failure through the reference's unwrap-then-open shape but as `NoSlot` through the SDK keystore's `(rs, gen)`-indexed shape (no DEK held for that generation — the reject happens before any key operation). Conformance runners accept `{Decrypt, NoSlot}` for that case only; every other case asserts the exact class.

## FIPS + PQC posture

- Default backend: RustCrypto (pure Rust, non-FIPS). `fips` feature re-bases primitives onto `aws-lc-rs`/`aws-lc-fips-sys` (pin as a pair, verify by compiling — F-260) and re-runs the full conformance gate. **v1 (`v1-ecdh-p256`) is FIPS-capable; v2 (X-Wing hybrid) is beyond-FIPS defense-in-depth, never a FIPS-mode tier.**
- v2 stays **inert** until: exact draft/RFC revision pinned in WIRE-FORMAT.md, spec KATs (not self-roundtrip) gate it, and any combiner-affecting change mints a **new suite id**.

## Bindings (Phase 2, lockstep)

Go, Python, TS/JS — thin hand-written wrappers over the C ABI, one version tag across all packages, each gated on the full conformance gate. Prebuilt natives resolved by the package manager (maturin abi3 wheels; napi-rs optionalDependencies; Go cgo), SHA-256 checksum files mandatory, never a postinstall download. Further languages/platforms demand-gated per ADR 1106.

**Mesh distribution.** On-mesh developers fetch the SDK from the mesh-internal `get.<site>.<zone>/sdk/` surface (a subdir of the goat-cli download surface) — the source tarball + prebuilt C ABI libraries (linux/darwin × amd64/arm64) of the `grant-crypto-sdk-v*` release, checksum-verified, no private-repo access needed. Build/release [`goat-cli-mesh-download.md`](goat-cli-mesh-download.md) §"SDK assets (grant-crypto)"; operator/developer runbook [`docs/operations/grant-crypto-sdk-install.md`](../operations/grant-crypto-sdk-install.md).

**The SDK ships its own documentation site.** A hand-authored static HTML+CSS site at `sdk/docs/site/` (overview, concepts, quickstart in all four languages, API + C-ABI reference, wire format, security, troubleshooting) rides inside the source tarball and is served, same bytes, at `get.<site>.<zone>/sdk/docs/` (a `grant-crypto-sdk-docs-<ver>` release asset unpacked by the goat-get role, pinned to the served release).
