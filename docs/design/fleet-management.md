> **60-second summary:** The project already does fleet management — it just does it in eleven places under eleven names, so the fleet-shaped questions ("is every node running what we decided?", "how does a change reach 3,000 nodes without breaking all of them?", "what happens to a node that was off for a month?") have no home and get re-answered per mechanism. This doc names the dimension, states fifteen rules with explicit provenance, maps them onto what is actually built, and decides the one architectural fork the tree left open: **convergence is pulled, not pushed.** The binding constraint is [ADR 0206](../adr/0206-island-mode-by-construction.md) — a site cut off for 30 days must still manage its own nodes — which disqualifies the central fleet controller that every commercial product in this category is built around. That constraint is not a caveat on the design; it *is* the design.

---

## 1. Why this is a dimension

Fleet management is not a component this project is missing. It is an axis that already runs through the substrate, unnamed:

- The **undo** primitive is live and CI-ratcheted to zero gap ([ADR 1060](../adr/1060-universal-deploy-rollback-ledger.md), live-fired M-075), while the **do** primitive on the same axis is a 12 KB serial playbook (`ops/ansible/coordinated-upgrade.yml`) whose only blast-radius control is `-e target=`.
- Two independent staged-rollout designs exist — [`progressive-config-rollout.md`](progressive-config-rollout.md) for configuration *activation* and `failure-isolation.md` §6 for a canary-site gate — and neither references the other.
- A node powered off for months does not converge on power-up (F-115, still active, engineered around by hand), and the doc that would close it ([`self-healing-substrate-sync.md`](self-healing-substrate-sync.md)) is design-only.
- There is no single authoritative list of the fleet's nodes. Four partial registries each answer a different question.
- Straggler remediation is an unbounded serial SSH fan-out over every peer IP (`peer-recover.sh`), in a project that has already written down why unbounded fan-out storms itself ([ADR 1081](../adr/1081-control-plane-storm-resilience.md), M-085).

Each of those is individually reasonable and individually tracked. What is missing is the axis they share, and therefore the place where a decision gets made once instead of five times. This doc is that place. It does not add a mechanism; it adds a frame, plus one decision (§5) that several queued mechanisms were waiting on.

**Why now, and why written for outside readers.** The next operational goatnet is the moment this axis stops being theoretical, and partner organizations standing up their own goatnets will inherit whatever posture is written down. §8 is addressed to them directly.

**Why the industry answer does not transfer intact.** Every mature product in this category — Rancher Fleet, Balena, Azure IoT Edge, AWS Greengrass, Foundries, Mender — is built around a control plane that is the ultimate authority, and degrades at the edge to *operating on last-known intent*. None of them lets a site **originate** new intent while islanded. That single property is the difference between a fleet whose sites are caches and a fleet whose sites are sovereign, and it is what [ADR 0206](../adr/0206-island-mode-by-construction.md) commits this project to. So the industry corpus is a source of mechanisms, not of shape.

## 2. What "fleet management" covers here

The dimension is the set of questions that are about *the population of nodes* rather than about any one node or any one service:

1. **Identity + inventory** — which nodes exist, in what lifecycle state, under whose custody.
2. **Intent** — what each node is supposed to be running and configured as, expressed as data.
3. **Convergence** — how a node gets from what it is to what it should be, including when it has been unreachable.
4. **Change propagation** — how a change reaches the population without the population failing at once.
5. **Undo** — how a change is reversed, per artifact class.
6. **Observation** — the difference between intent and reality, per node, honestly graded.
7. **Remediation** — what happens to a node that is diverged, wedged, or unreachable.

## 3. The principles

Fifteen rules in five clusters. Each carries its provenance:

- **ADOPTED** — taken from industry practice; the origin is cited.
- **DERIVED** — follows from this project's own founding decisions; the founding doc and section are cited.
- **ORIGINATED** — neither source covered it. The gap is named and the rationale given. These are the four rules this project is establishing rather than inheriting, and they are the ones a partner should read hardest.

### A. Authority — where fleet functions are allowed to live

**P1. The fleet-management plane is expendable. — DERIVED**
Its total loss degrades *visibility and change*, never *operation*. A node whose fleet plane is unreachable keeps doing its job; it simply stops learning about new intent and stops being observable.
*Source:* [ADR 0201](../adr/0201-enrollment-vs-mesh-op-separation.md) §Decision — the management server "is not in the path of any actual traffic" after enrollment; `architecture.md` — "the management plane is expendable at the tactical edge."
*Test:* kill the fleet plane entirely. If any node's mission function degrades, P1 is violated.

**P2. A partitioned site manages its own nodes. — DERIVED**
Every fleet function a site needs to keep its own nodes correct — enroll, converge, authenticate, roll back, observe — resolves against site-local authority. Cross-site and cloud reachability improve the picture; they are never prerequisites.
*Source:* [ADR 0206](../adr/0206-island-mode-by-construction.md) §Decision — "no decision the system makes during steady-state operation requires reaching another site"; Kubernetes/etcd/Consul/Raft coordinators and centralized service discovery are named and rejected there, and "best-effort island mode is not acceptable for the management plane."
*Test:* the 30-day question. Sever a site from every other site and from the cloud for 30 days. Every fleet operation is either "still works" or "explicitly and visibly unavailable." A silent no-op is the failure.
*Industry note:* Azure IoT Edge's edgeHub authenticating modules and downstream devices *on IoT Hub's behalf* while offline is the closest commercial analogue and validates the shape. It is also where the analogy stops — see P3.

**P3. An islanded site may originate intent; rejoin reconciles it. — ORIGINATED**
A site cut off is not restricted to replaying the last intent it received. It may declare new intent for its own nodes — a pin change to work around a local failure, a new node enrolled, a service disabled — and that intent is first-class. On rejoin, the site's originated intent and the fleet's intent are reconciled by a declared per-fact policy, not by last-writer-wins on a whole document.
*Gap this fills:* no commercial product in the survey supports it. Balena, Azure IoT Edge, and Greengrass all degrade to *operate on last-known intent* — the site is a cache, never an author. The §6.7 supplemental survey adds the sharpest case: **SpectroCloud Palette Edge does let a disconnected site author intent locally, through its Local UI — and documents that pairing that site to the management plane is a one-way door, after which "local cluster operations will no longer be permitted."** Local authorship and fleet membership are offered as an exclusive, irreversible product choice, never as a partition-time behaviour. Red Hat's flightctl has no local writer at all, and a hand-forged local spec lands the device in `ConflictPaused` on reconnect. Project canon asserts site autonomy ([ADR 0206](../adr/0206-island-mode-by-construction.md)) but has never stated it for fleet *intent* specifically, and [ADR 0224](../adr/0224-progressive-config-rollout-with-auto-revert.md) §3.4's partition policy covers only whether a *received* change activates, not whether a cut-off site may author one.
*The smallest safe foothold, recorded and deliberately not taken:* a per-node opt-out flag set in-band on the node itself — Cluster API's `exclude-node-draining` shape (§6.7 D) — is site-authored intent whose only expressible content is "leave me alone," and it needs no rejoin-reconciliation policy because the fleet's answer on rejoin is unambiguous. It is the one form of P3 that does not require solving P3. It is **rejected for now** on coherence grounds — it mints a second intent authority on the node for a case nothing is asking for, and §7 sequences islanded origination last on purpose — but it is the shape to reach for first if that sequencing ever changes.
*Rationale:* a site that cannot author intent while islanded is a site whose operators must wait for the WAN to fix a local problem — which is precisely the dependency the whole architecture exists to remove. The honest counterweight: reconciliation-on-rejoin is a genuinely harder problem than anything else in this doc, and it is **not solved**. §7 sequences it last, deliberately, and §8 tells partners to defer it.
*Test:* an operation class that cannot state its rejoin-reconciliation rule may not be made islanded-authorable. Defaulting to "the fleet wins" is an acceptable rule; leaving it unstated is not.

**P4. Inventory is derived from self-declaration, never maintained. — DERIVED**
The answer to "what nodes do we have" is computed from what nodes declare about themselves — mesh membership, fabric identity, role declarations, health publications — not from a database an operator keeps current.
*Source:* [ADR 0208](../adr/0208-phoenix-native-peer-discipline.md) §Decision — role declaration via Zenoh key expressions, capability-based discovery "not via hardcoded hostnames or service IPs," and the SCA-R note that "Zenoh role declarations are the inventory"; [ADR 0224](../adr/0224-progressive-config-rollout-with-auto-revert.md) §3.2 — cohorts are derived at activation time, "there is no separate cohort registry to maintain."
*Recorded conflict with industry:* this is a direct contradiction of the dominant commercial pattern. Azure Device Registry states that the cloud registry is the source of truth and devices are created or modified only through it; AWS IoT's fleet index is a maintained join of registry, shadow, and connectivity. **The adaptation:** keep the industry's *join* (identity ⊕ intent ⊕ observed state in one queryable view — it is right that a registry knowing only identity answers no operational question) and reject its *authority* (a maintained registry that a site must reach). `goat who` ([ADR 1047](../adr/1047-goat-who-identity-cop.md)) is already exactly this shape — it reconciles four layers and is deliberately a reader, not a registry. The unresolved residue is real and named as G4 in §7: derived inventory still needs *one* named answer to "which layer is authoritative for the set of all nodes," and today there isn't one.

### B. Intent — what a node is supposed to be

**P5. Intent is data, separate from the actuator. — ADOPTED**
What a node should run is a committed, versioned, inspectable, diffable artifact. Ansible remains the actuator that applies it; it is not the place the intent lives. Reading intent must not require running a playbook or replaying a history of playbook runs.
*Origin:* Configuration-as-Data — Brian Grant / kpt / Config Sync, which separates config data (source of truth, stored apart from live state, uniformly serializable) from *actuation*; OpenGitOps Principles v1.0.0 ("Declarative", "Versioned and Immutable").
*Local precedent that this generalizes:* the F-197 arc. A hand-synced pair of files became a generator (`ops/dns/generate-mesh-hosts.py`, `--check` in CI) and that class of drift stopped recurring. `ops/pins/fleet-pins.yaml` (`environment-parity.md` §3, built 2026-08-02) is the same move applied to image pins and is this doc's intent substrate.

**P6. Pins move; tags never float. — DERIVED**
A fleet change is a reviewed move of a pinned digest. Auto-update-to-newest is structurally forbidden as a fleet default, and multi-arch pins reference the **index** digest, not a per-arch manifest digest.
*Source:* [`engineering-baseline.md`](https://github.com/usareur-af/goatdocs/blob/main/docs/design/engineering-baseline.md) §6.1 and [ADR 0703](../adr/0703-pinned-digests-and-pin-regression-ci.md) — "`latest` is a recipe for 'works on my machine'"; [ADR 0859](../adr/0859-easy-rollback-engineering-principle.md) records the operational consequence directly (panoscope's `:latest` pull meant the prior-good image had already been overwritten when the operator wanted to roll back); F-245 for the multi-arch index-digest rule.
*Industry corroboration:* digest pinning is treated as a *correctness* property, not only a security one — with a mutable tag, a rollback to a previous commit re-pulls the overwritten image and the rollback fails silently.

**P7. Intent carries provenance and age, and a node reports the age of the intent it converged against. — ORIGINATED**
"Converged" is not a boolean. A node reports *which version of intent* it reconciled against and *how old that intent was when it reconciled*, so that "converged against 9-day-old intent" is distinguishable from "converged against current intent" — and both are distinguishable from "has not reported."
*Gap this fills:* TUF and Uptane solve freshness at the metadata layer with short-lived timestamp/snapshot roles and expiry, and a strict client refuses to update against expired metadata — which is unusable at a site deliberately offline for 30 days. Project canon grades the freshness of a *reading* ([`fabric-health-surface.md`](fabric-health-surface.md) §1a rule 2: sample count, window, and vantage travel with every value) but has no vocabulary for the freshness of the *intent* a node is complying with. Neither source covers the sentence an operator actually needs.
*Rationale:* it converts island mode from an excuse into a measurement. Under P15 a node that is perfectly converged against stale intent renders as green today — which is a false green with a mechanism behind it. Grading intent age instead of expiring it keeps the TUF freshness guarantee's *information* without inheriting its fail-closed behaviour, which island mode cannot accept.
*Test:* every fleet compliance statement must be expressible as "N nodes match intent version V, oldest converged-against intent is D days old, M nodes have not reported in H hours." A statement that cannot carry those three clauses is not grounded.

### C. Convergence — how a node gets there

**P8. Convergence is pulled, and every fleet loop is level-triggered. — ADOPTED, adapted**
The node fetches intent and reconciles itself. The fleet plane publishes intent and collects reports; it does not drive execution. This is the §5 decision; the full argument, the retained push exceptions, and the costs are there.
*Origin:* OpenGitOps Principles v1.0.0 ("Pulled Automatically", "Continuously Reconciled"); Rancher Fleet's two-stage pull; Balena's supervisor reconciling toward a locally-cached target state.
*Adaptation:* the industry pull model pulls from a reachable central store. Here the node pulls from a **site-local replica** of signed intent, so the pull completes with zero WAN — see §5.
*The property underneath, named because §5 relies on it without stating it* (added by the §6.7 survey): Kubernetes' architecture design principles put it best — "functionality must be *level-based*, meaning the system must operate correctly given the desired state and the current/observed state, regardless of how many intermediate state updates may have been missed. Edge-triggered behavior must be just an optimization." Every fleet loop here re-derives its action from (intent, observed state) on each pass, never from a change event. This is what makes §5's argument structural rather than situational: a push run from an operator laptop is edge-triggered *by construction* — its correctness depends on the laptop having been present and correct at every transition, and a single missed run is a permanently wrong node with no correcting event that will ever be re-sent. A missed pull pass costs latency and never correctness.
*Test:* delete every record of what a loop has already done. If it cannot compute its next action from current intent and current observed state alone, it is edge-triggered and will drift silently.

**P9. Load decays under failure. — DERIVED**
Any fleet loop — reconcile poll, report publish, remediation retry — must place *less* load on the network as failures accumulate, never more. Jittered exponential backoff, a circuit breaker after repeated failure, event-driven re-dial on a connectivity signal.
*Source:* [ADR 1081](../adr/1081-control-plane-storm-resilience.md) / [`control-plane-storm-resilience.md`](control-plane-storm-resilience.md) §L1, stated there as the principle: "a control plane whose load decays when delivery fails cannot storm itself." The measured failure it comes from is in §1. §L2 adds a hard ordering constraint: server-side shedding *before* client backoff made it worse — M-086 cut server load 93% while link ingress rose.
*Test:* model the loop with every node failing to reach intent. If aggregate bytes-per-hour rises or stays flat, the loop is a storm generator. A fixed-cadence unjittered poll fails this test.

**P10. Intent is queued, not delivered. — ADOPTED**
A change targeting an unreachable node persists and applies when the node returns. Fire-and-forget against an absent node is not a fleet operation; it is a coin flip that reads as success.
*Origin:* Balena — offline devices do not update but the request stays queued and applies on reconnect; Azure IoT Edge — after one initial sync a device operates indefinitely offline and reconciles desired-vs-reported properties on reconnect, replaying stored messages in order.
*Why it is load-bearing here specifically:* the fabric has **no delivery lifecycle** — no acks, no retries, no dead-letter queue; `put` is fire-and-forget and storages are caches ([`zenoh-brokerless-consequences.md`](zenoh-brokerless-consequences.md), F-178). A push-and-assume-convergence design has no mechanism that could ever tell it otherwise. Queueing is not an optimization here; it is the only sound shape.

**P11. The fleet agent is a coprocessor. — DERIVED**
Whatever runs on a node on fleet management's behalf is evictable, resource-bounded, and structurally incapable of taking the node's mission function down with it. It says what it cannot do rather than silently no-opping.
*Source:* [ADR 0863](../adr/0863-resilient-end-node-design-philosophy.md) §Decision principle 1 (canonical workhorse + optional coprocessor; augmentations "never replace it, and their failure mode never tears it down") and principle 6 ("hidden features that silently do nothing are forbidden — they erode operator trust and make degradation invisible"); [ADR 0214](../adr/0214-failure-isolation-four-pattern.md) bulkhead pattern.
*Local anti-precedent, already written down:* [`wg-cp0-peer-lifecycle.md`](wg-cp0-peer-lifecycle.md) records why a fleet-wide push handler that fires on every allowlist push is wrong: it is disruptive on every push (every client re-handshakes when one peer is added) and it can mask an outage. Any fleet mechanism must demonstrate it does neither.

### D. Change — how the fleet moves

**P12. Waves are per-site, halt automatically, and never advance on unknown. — ADOPTED, with an ORIGINATED clause**
A change reaches the fleet in time-separated waves whose natural unit is the **site**, with halt criteria declared before the wave starts. One wave at a time. A failing wave stops everything downstream.
*Origin:* Google SRE Workbook "Canarying Releases" — a canary is "a partial and time-limited deployment"; the rest of the fleet is the control; never compare before/after, because "time is one of the biggest sources of change in observed metrics"; cap the criteria at no more than a dozen; run one canary at a time. Rancher Fleet ships `maxUnavailablePartitions: 0` as the default. Mender's phased shape is 5% → 15% → 80% with ~2 days between phases.
*Project-canon corroboration:* staged rollout is not an import needing justification — [ADR 0214](../adr/0214-failure-isolation-four-pattern.md) already names "canary deploys; staged rollouts; auto-rollback" as its blast-radius mechanisms, and records honestly that as of 2026-04-25 the rollout of those items had not begun.
*The site-first clause is the adaptation:* a wave that spans all sites at 5% each has a 100% site blast radius. Site is the failure and autonomy boundary here, so it is the wave unit, and per-node staging happens *within* a site.
**The ORIGINATED clause — unknown blocks promotion.** Wave promotion requires *positive confirmation* from a declared fraction of the wave. A node that has not reported counts **against** promotion, never toward it. SRE-style canarying assumes the canary is observable; a node in island mode produces no signal for hours or days, so "no bad news" is not evidence of health. No source in the survey states this, because no surveyed product treats multi-day unobservability as normal. This is where P15's honesty grammar becomes a *gate* rather than a display rule.

**P13. An operation class is not defined until it declares transport, partition-mode, artifact class, and blast unit. — ORIGINATED (composition)**
Before a fleet operation can be built, its class declares four things:
| Axis | Values | Inherited from |
|---|---|---|
| Transport | `pull` (default) / `push` (exception, argued) | §5, this doc |
| Partition-mode | `activate-on-arrival` / `hold-until-rejoin` | [ADR 0224](../adr/0224-progressive-config-rollout-with-auto-revert.md) §3.4 |
| Artifact class | `image` / `config` / `data` / `cert` / `forward-only` | [ADR 1060](../adr/1060-universal-deploy-rollback-ledger.md), `ops/scripts/rollback.sh` dispatch |
| Blast unit | `node` / `site` / `fleet` | §P12 |
*Gap this fills:* all four axes exist in canon, in three different documents, and nothing composes them. The result is that a new fleet operation can be built having answered one of the four and never noticed the other three — which is how `coordinated-upgrade.yml` came to exist with a blast unit of `fleet` and no declared partition-mode.
*Rationale:* the four are not independent in practice. `push` + `hold-until-rejoin` is incoherent (nothing to hold). `data` or `cert` artifact class means undo is a lie and the class must refuse with a restore or rotate pointer instead — [ADR 0859](../adr/0859-easy-rollback-engineering-principle.md) is explicit that conflating those into "rollback" creates an unsafe impression. Making the declaration a single required act catches those at design time rather than at 3am.
*Test:* grep the operation's design for four labels. Three is a finding.

**P14. Verification is fail-closed at the node. — ADOPTED, adapted**
A node verifies what it is about to apply against a local trust root, at apply time, and a node that cannot verify **refuses and reports diverged** — it does not proceed, and it does not go quiet.
*Origin:* deploy-time verification as policy — fetch by digest, fetch signatures and attestations, validate against policy, proceed only on pass. Signing without verification is theatre.
*Corroboration, and its cautionary half* (added by the §6.7 survey): Kairos implements exactly this shape — its upgrade path calls `CosignVerify` inside `DumpSource` and aborts the upgrade when verification fails, on the node, at apply time. It also ships that verification **off** in its own NVIDIA Jetson cloud-config (`cosign: false, verify: false`) — a fail-closed default disabled precisely on the constrained hardware where a substitution is hardest to notice. A verification default that ships off is the same class of failure as a check wired into no workflow (`check-zenoh-pinning.sh`, `environment-parity.md` §1), and this rule is not satisfied by a mechanism that exists in a code path nothing enables.
*Adaptation, and the reason it is not simply adopted:* keyless Sigstore is unusable as specified at the denied edge — signing needs OIDC and Fulcio reachable, and verification needs Rekor unless the inclusion proof is bundled into the artifact. The adaptation is (a) bundle the inclusion proof so nodes verify fully offline, (b) a local trust root at each site, (c) fail-closed on verification failure.
*The pattern to copy is already in the tree and is cheaper than the industry one:* [`name-fallback-resolver.md`](name-fallback-resolver.md) ([ADR 1082](../adr/1082-name-fallback-resolver-signed-snapshots.md), phase 1 built) distributes signed fleet state using a monotonic SOA-style serial, a declared TTL, and a detached ECDSA P-256 signature from **the site's existing offline CA — no new key infrastructure** — with five-state staleness grading where `expired` and `unverified` both refuse. It bounds replay to old-valid content (cannot forge, cannot roll back) and works over sneakernet by construction. That is a complete signed-fleet-state distribution pattern, already built, and §7 reuses it rather than importing TUF.
*The Uptane idea worth keeping without building Uptane:* split the keys by function — the key that authorizes *what may be installed* stays offline; the key that targets *what should be installed on node N now* may be online. That maps cleanly onto release artifacts versus per-goatnet pins.

### E. Honesty

**P15. Fleet readings are honesty-graded and self-dating. — DERIVED**
Every fleet reading grades under the five-state grammar (`green` / `amber` / `red` / `idle` / `unmetered`), carries its grounding (`n`, window, vantage), and distinguishes measured from inferred from assumed. A node that has not reported is **unknown**, never compliant. A percentage without a denominator is not a reading. "100% compliant" that is really "0 nodes reported" is the specific failure this rule exists to make impossible.
*Source:* [`fabric-health-surface.md`](fabric-health-surface.md) §1a rules 1–5 — "a measurement that looks meaningful but isn't is worse than no measurement — a false 'green' gets believed"; "honest 'unknown' beats false 'green'"; "these rules govern not just v1 but every layer added later." [`environment-health-surface.md`](environment-health-surface.md) supplies the envelope and the reveal-only posture. [ADR 1022](../adr/1022-zenoh-denial-observability.md) / F-177 supply the reason it is not optional: denial and drop are **silent at both ends**, so absence of error is never evidence of convergence.
*Industry corroboration, negatively:* Microsoft documents that a device with no internet connectivity can still read **200 OK** in the Azure portal, because an offline EdgeAgent cannot report status. That is default-green-on-silence in a first-party product, stated as a known limitation. It is the best available citation for why silence must never render as health.

## 4. The reference model against what is actually built

Honest maturity per function. "Built" means code on main; "live" means deployed with a cited verification artifact.

## 5. Decision: convergence is pulled

**A node converges by fetching intent and reconciling itself against it, on a jittered interval, from a site-local replica of signed intent. The fleet plane publishes intent and collects reports; it never drives execution.**

Three constraints settle this, and they all point the same way:

1. **There is no delivery lifecycle.** The fabric has no acks, no retries, no dead-letter queue; `put` is fire-and-forget and storages are caches ([`zenoh-brokerless-consequences.md`](zenoh-brokerless-consequences.md), F-178). Denial and drop are silent at both ends (F-177, [ADR 1022](../adr/1022-zenoh-denial-observability.md)). A push therefore cannot know it landed, and no amount of engineering on the push side changes that without re-introducing the broker the project rejected. A pull inverts the burden: the node knows whether it fetched, and its report is the ack.

2. **Load must decay under failure.** A push fan-out retried against unreachable nodes is exactly the shape M-085 measured, where "weather starts it; behavior sustains it." A jittered pull with backoff and a circuit breaker decays by construction (P9). The existing straggler path (`peer-recover.sh`, unbounded serial SSH over every peer IP) is the same defect not yet removed.

3. **Island mode.** A push converges the nodes reachable during the run, and at the denied edge the reachable set is the wrong set — it is "whatever was up on Tuesday." A pull converges a node whenever *the node* can reach intent, which, because the replica is site-local, is true even with the WAN down for 30 days.

### What push is retained for

Pull loses cross-host ordering — that is the real cost, and it is well documented in the ansible-pull tradeoff (no controller means no orchestration sequencing, and debugging is harder). So push is retained, as a declared exception under P13, for operations that genuinely require coordinated ordering across hosts. Today that is one: `ops/ansible/coordinated-upgrade.yml`'s stop-all → migrate-on-one → verify → restart-serially sequence, where the Postgres/Spock migration must happen exactly once and in order.

**Those operations are explicitly unavailable in island mode**, and that is stated rather than papered over: a cut-off site cannot run a coordinated multi-host migration, because coordination is precisely what it lacks. This is the [ADR 0201](../adr/0201-enrollment-vs-mesh-op-separation.md) classification applied to fleet operations — occasional and latency-tolerant operations may require reachability; steady-state convergence may not.

### What this decision is not

It is not a workload scheduler and does not fire [ADR 0207](../adr/0207-docker-compose-orchestration.md)'s reopen triggers. It moves pins and renders config on a node that already knows what it is; it does not place workloads across a cluster, and it introduces no quorum, no leader election, and no consensus on cohort advance ([ADR 0206](../adr/0206-island-mode-by-construction.md) rejects those by name).

It also does not create a second convergence engine. [`engineering-baseline.md`](https://github.com/usareur-af/goatdocs/blob/main/docs/design/engineering-baseline.md) §2.2/§12.3 is explicit that drift is fixed by re-running the playbook, and two authorities over one host is a design decision that must be made rather than stumbled into. **The decision made here is: there is one convergence engine — Ansible — and the pull loop invokes it.** The node fetches intent, and if intent differs from what it last applied, it runs the existing idempotent play against itself locally. What is new is the *trigger* and the *transport*, not the actuator. That keeps `-e`-free, git-tracked, re-runnable semantics (C5) intact and avoids an agent that can overwrite what Ansible converges.

### Where this leaves the queued question

Backlog item 50J.2 states the fork verbatim — "Lambda fan-out vs DynamoDB Streams + per-relay agent that watches the stream and applies — pick one." Picked: **watch-and-apply**, with the stream replaced by a signed, versioned intent document and the watch replaced by a jittered pull, because the cloud-hosted stream is itself an [ADR 0206](../adr/0206-island-mode-by-construction.md) dependency.

## 6. Recorded conflicts and adaptations

Where industry practice and the project's constraints disagree, the reasoning is the exemplar value. Six conflicts, each with what was kept and what was refused.

**6.1 Staged rollout stops at Phoenix-native peers.**
[ADR 0224](../adr/0224-progressive-config-rollout-with-auto-revert.md) §3.6 scopes its pattern to Phoenix-native peers and states that substrate — Spock, Zenoh routers, Postgres, Caddy/Traefik, kernel, OS packages — "continues to use traditional Ansible-deploy procedures," because the boundary is enforced by cohort derivation and only Phoenix-native peers declare consumed key expressions. But substrate deploys are exactly where fleet-wide blast radius lives. **Decision:** extend the wave/halt/auto-revert *pattern* to substrate deploys, with cohorts derived from the existing site and node-class dimensions of the identity grammar (ADR 1043) rather than from consumed key expressions. This is a new decision recorded in [ADR 1109](../adr/1109-fleet-management-dimension-and-pull-convergence.md) and amended into 0224 — not an implicit read-through. 0224's *deferred-activation* mechanism does **not** extend: substrate cannot defer activation, so a substrate wave is staged at the deploy step, and its safety property is health-gated automatic revert rather than delayed activation.

**6.2 The central controller.**
Every product in the survey has one. [ADR 0206](../adr/0206-island-mode-by-construction.md) rejects it by name, along with etcd, Consul, Raft coordinators, and centralized service discovery. **Kept:** the *join* of identity, intent, and observed state into one queryable view (AWS's fleet-index shape) — a registry that knows only identity answers no operational question. **Refused:** its authority. The sanctioned form is already written down as the actor-relationship-graph stance ([ADR 1065](../adr/1065-graph-engine-property-graph-read-model.md)): a derived read-only projection at the rear plane, never at the tactical edge, brokerless-safe because it sits in no enforcement path. A cross-goatnet fleet view may render; it may not decide.

**6.3 Short-lived credentials versus 30-day island mode.**
SPIFFE's model — minutes-to-hours SVIDs, auto-rotated, revocation by ceasing issuance — is directly incompatible with a site offline for weeks. **Adaptation: lifetime tiers by whether the site has a local issuer.** A site with a local issuing authority uses short-lived credentials; a site without one uses longer-lived attested credentials, and that tier is explicitly enumerated and audited rather than being the accidental default. The generic renewal rule is adopted unchanged: renew at ⅔ of lifetime, per credential, automatically. Project mechanisms already cover the machine half — rotation is in-place leaf re-issue and covers machines explicitly ([ADR 1044](../adr/1044-credential-rotation-in-place-reissue.md), live-fired M-069), and revocation cascades along **containment, not custody** ([ADR 1031](../adr/1031-credential-revocation-mesh-first-offboarding.md)), so revoking a departing operator does not take down every system they enrolled.

**6.4 TUF/Uptane freshness versus deliberate offline.**
Metadata expiry defends against freeze attacks; PEP 458's practice is timestamp and snapshot expiring in about a day. A node offline for 30 days sees expired metadata and must, strictly, refuse. **Adaptation: grade, do not fail open, and do not fail closed on age alone.** Keep signing and monotonic versioning (which kill rollback and mix-and-match), keep expiry as *information*, and make intent age a first-class reported field (P7) instead of a refusal trigger. Verification failure remains fail-closed (P14); *staleness* is graded. Do not build Uptane; keep its two-key split.

**6.5 Immutable-OS / image-mode fleets.**
OSTree, bootc, and Talos remove drift by removing mutability, and greenboot's health-gated automatic rollback is the highest-value piece. The fleet here is Ansible-and-Compose on Ubuntu and Ubuntu-for-Tegra with hardware-specific Jetson requirements, and image mode is not on the table. **Corrected 2026-08-04 by the §6.7 survey:** this section originally added "and full-image swaps are bandwidth-hostile over satellite regardless," which is true of Kairos — its maintainers state that every node re-downloads the whole image on every upgrade — and **false of bootc**, which fetches only layers not already present and deduplicates below the layer at file level via ostree. The rejection stands, on hardware rather than on bandwidth: there is no bootc equivalent of the L4T/Tegra kernel and BSP wiring, and the Orin is the constrained node. Keeping the wrong reason would have made a correct decision unreviewable. **Kept:** health-gated automatic revert after every change — separable from image mode and implementable on this fleet today; retain N-1 locally so rollback needs no network (the rollback ledger already does this); treat the service layer as immutable even though the OS is not (digest pins, generated config, and a check that a managed file was hand-edited is a *finding* — built repo-side by CF-4's declared render watch-sets, `consistency-foundation.md` §5.2a: a hand-edited watched render grades `unaccountable`). **Refused:** the image-swap delivery model. Talos's ban on shell access is adopted as *policy* rather than enforcement, and the project already states it: "no hand-edited servers… if it's not in git, it didn't happen" ([`engineering-baseline.md`](https://github.com/usareur-af/goatdocs/blob/main/docs/design/engineering-baseline.md) §12.3).

**6.6 SaaS fleet management.**
Intune, JAMF, Tanium, Datadog-style agents. [`deliberate-deltas.md`](https://github.com/usareur-af/goatdocs/blob/main/docs/design/deliberate-deltas.md) §1.1 disqualifies cloud as a store for data-at-rest, and fleet state is data-at-rest. **Refused outright as a store of fleet state.** The only shape that could ever qualify is the PagerDuty carve-out's: a named exception with its own ADR, a strict metadata-only data boundary, and a load-bearing reason that turns on surviving the failure domain it watches. No such proposal is made here.

## 6.7 Supplemental survey — 2026-08-04

The original survey (§6.1–§6.6) covered the fleet-controller products. This pass covers four families it did not: **Kairos** (the open-source OS-as-OCI meta-distribution), **SpectroCloud Palette** (the proprietary layered-profile product built on it), **Ansible Tower/AWX**, and **Kubernetes fleet-operations patterns** — the last stolen as patterns only, since the Kubernetes substrate rejection is settled ([`deliberate-deltas.md`](https://github.com/usareur-af/goatdocs/blob/main/docs/design/deliberate-deltas.md) §9, [ADR 0207](../adr/0207-docker-compose-orchestration.md)) and nothing here reopens it.

Claims are tagged **[E]** where they come from a primary source or from this tree, and **[I]** where they are inference. The columns are: what the pattern is, where it comes from, the verdict, the reasoning against the named constraint, and what it changes here.

**The curation rule this pass was held to, and why it is stricter than the first survey's** (operator direction, 2026-08-04). A survey's failure mode is a capability shopping list: every pattern is interesting, each looks cheap in isolation, and the sum is a system nobody can describe. So the bar here is not "is this good," it is:

1. **Bias to reject.** An adoption must either make the system *simpler* — collapse two things into one — or close a gap this doc already names. "Interesting" is a rejection.
2. **A hard cap of four adoptions across the whole pass.** Candidates past the cap become one-line rejections whose stated reason is **coherence budget**, so they are recorded and recoverable rather than silently dropped.
3. **Every adoption states in one sentence how it reduces to the existing spine** — `IntentV1` × `ConsistencyV1` × one grading library × pull convergence × retire-on-supersede. A pattern that needs a concept which does not reduce to that spine is rejected; the need for a new concept is the signal, not the opportunity.
4. **Prefer adoptions that retire or fold something already planned** over adoptions that add a workstream.

**The result, over 24 candidates: three ADOPT, one ADAPT, fourteen REJECT** — of which four are rejected as *already covered by something this project has* and three on *coherence budget*. Three further rows are **folded into adoption 2** as its sources rather than counted separately, and three are notes that corroborate an existing rule without adopting anything. **No new backlog slug is minted.** All four adoptions land inside mechanisms already on the roadmap, and adoption 2 *deletes* a workstream this pass had drafted before the rule was applied. The elegance test is at the end of the section, and it is what the pass is accountable to.

### The four adoptions, and what each one removes

Each states its spine reduction in one sentence, because a pattern that cannot state one is not adopted.

**1. Level-triggered reconciliation → P8.** *Reduces:* the whole spine becomes one level-triggered loop — `IntentV1` is desired state, `ConsistencyV1` is observed state, the grading library is the comparison, and the pull loop re-derives its action from the pair on every pass. *Removes:* §5's three situational arguments for pull collapse into one structural property. Costs zero substrate.

**2. The site disruption budget → FM-4 and FM-6.** *Reduces:* an operation declares its blast unit and halt criterion under P13 exactly as it already must, and the budget is checked against `EnvHealthV1` — no new vocabulary. *Removes:* three would-be mechanisms become one. "Do not disrupt more than N of a site at once" (waves) and "do not remediate more than N at once" (self-heal) are the same invariant read against two actors, and a reboot is simply a wave of blast unit `node` — so the reboot-coordination daemon this pass had drafted is **deleted rather than backlogged**, and the immediate tree defect closes with `serial:` and a health gate on a play that already exists.

**3. `IntentV1` generation retention → `consistency-foundation.md` §3.3a.** *Reduces:* one optional field inside the artifact every consumer already reads. *Removes:* the alternative — either the grading library grows a second input path (git history, unavailable to a meter, a console, or an FM-2 node) or `unaccountable` is dropped and the canon loses a distinction it deliberately added. Proposed, not applied; flagged for orchestrator review.

**4. The actuator as a pinned row → FM-2.** *Reduces:* the actuator stops being a special unmodeled thing and becomes one more row in `fleet-pins.yaml` → `IntentV1` → `ConsistencyV1` → the grading library. *Removes:* the "and whatever Ansible the laptop happens to have" caveat that D3's "one convergence engine" currently rests on. The one adoption that adds rather than removes, and it is a row plus a wrapper flag, not a track.

Three corrections ride along and are not adoptions: **§6.5**'s bandwidth premise is fixed (false of bootc, so a correct rejection stops resting on an incorrect reason); **P14** gains Kairos's verify-at-apply and the sharper note that Kairos ships it *off* on Jetson; **P3** gains Palette Edge as its fifth and strongest witness. **§4**'s Undo row gains one clause stating that undo stops at the container edge.

**No new backlog slug is minted.** Everything lands in FM-2, FM-4, FM-6, P8, P14, P3, §4, §6.5, or the `consistency-foundation` amendment.

### The elegance test

*After this pass, is the approach describable in fewer sentences than before?*

Before: convergence is pulled, for three reasons; waves stage change; a self-heal loop remediates nodes; reboots are whatever the play does; the actuator is whatever ran the play; and a node is graded against intent.

After: **the fleet is one level-triggered loop — each node fetches `IntentV1`, reconciles itself with a pinned actuator, and publishes `ConsistencyV1`; one library grades the pair; and any actor that would disrupt a site first checks one declared budget.** That is one sentence covering what previously took six, and it is the reason the cap was worth enforcing: the two candidates that most tempted this pass into a fifth and sixth adoption (a reboot daemon, a fifth P13 axis) are precisely the two that would have made that sentence longer.

**What this pass did not find.** No product in these four families lets a site author intent while islanded and reconcile it on rejoin — P3 stands unserved, and Palette's one-way door is the closest anyone comes. Nothing solves override provenance either: nothing surveyed can answer "which layer set this value," so that stays an open question rather than a thing to import.

## 7. Roadmap — sequenced, backlog-gated

Ordered by leverage per unit of new substrate. Every increment states its gate. Block numbers are minted at backlog→in-flight promotion, not here.

**FM-1 — Convergence reporting as a `ConsistencyV1` arm.** Each node self-publishes the component refs it is running, its config render hash, and the version and age of the intent it converged against (P7), on the existing `EnvHealthV1` envelope; a passive reader rolls up. No new surface, no new authority — this is parity WS7 with P7's intent-age field added. **Absorption obligation:** FM-1's landing change retires the interim consistency artifacts it supersedes — the committed stage-1 parity report file is deleted (its resolver survives as the intent-provider library), per the maturation contract in `environment-parity.md` §5. Consistency surfaces converge on `goat health`; they do not accumulate beside it.
*Why first:* it is the cheapest increment on the list, it makes every later increment measurable, and until it exists P12's unknown-blocks-promotion gate has no input.
*Gate to in-flight:* the `oneof` arm and proto land with one publishing node class.
*Gate to canon:* deployed on one goatnet, one measurement artifact showing a *true* skew row that was previously invisible.
**Now specified in full — `consistency-foundation.md` ([ADR 1110](../adr/1110-typed-consistency-foundation-and-console.md)), which is the primary doc for this increment.** It is CF-3 there, and it turned out to have two prerequisites this row did not name: the typed intent artifact every consumer reads (CF-1, P5 made concrete) and the single grading library that keeps the comparison from being re-derived per surface (CF-2). The absorption obligation above is honored explicitly there, and **executed on 2026-08-04**: CF-3's landing change deleted `ops/pins/parity-report.md` and moved its CI gate onto `intent.json`. The intent-age rule is sharpened too: age is *reported* always and *graded* only when the node's generation is not the current one, because a goatnet whose config has not changed in 90 days is correct, not stale. This row is not re-planned here; read that doc for the mechanism.

**FM-2 — Pull reconcile for one operation class, one node class.** A site-local signed intent replica plus a jittered fetch that invokes the existing idempotent play when intent differs from last-applied. Scope it to pin-class intent on mgmt-hosts.
*Prerequisite, from the §6.7 survey — the actuator becomes an ordinary pinned row.* D3 makes Ansible the one convergence engine and this increment invokes it on a node that has no operator laptop, so there must be a *defined* Ansible to invoke: a digest-pinned actuator image whose pin is a row in `ops/pins/fleet-pins.yaml` like every other image, carried into `IntentV1`, and reported in the node's convergence record — so "what is this node running" finally includes the thing that put it there. `ansible-preflight.sh` fuses the *tree* against a stale checkout and nothing fuses the *interpreter*, which is the F-172 failure mode one layer down. Two constraints on how it is built: it is a plain Chainguard-based image rather than an `ansible-builder` product, because that tool supports only RPM-based bases while [ADR 0700](../adr/0700-chainguard-first.md) is Chainguard-first and `ansible-runner` needs only an image with Ansible in it; and it is scoped to the mgmt-host, **not** the operator laptop, whose local-container-runtime and path dependencies (`.envrc.local.d`, `aws-vault`, `delegate_to: localhost`) are a separate decision with separate costs.
*Why second:* it proves P8/P9/P10 on the narrowest possible surface and is the seed of G7 (a node offline for months converging on power-up).
*Gate to in-flight:* the loop runs on one host with intent authored in `ops/pins/fleet-pins.yaml`.
*Gate to canon:* a node deliberately powered off for ≥7 days converges on power-up with no operator keystroke, and the loop's aggregate load is *measured* to decay under an induced total-failure condition (P9's test is not satisfiable by inspection).

**FM-3 — Name the node registry of record.** A decision, not a store: which of the four existing registries is authoritative for "the set of all nodes," what the other three are, and how a machine row gets created at enrollment so systems appear in the declared roster beside persons.
*Why third:* it costs no new substrate and unblocks the inventory half of FM-1's rollup. It also has to happen before waves, because a cohort you cannot enumerate is not a cohort.
*Gate to in-flight:* the ADR amendment or design section naming the authority lands.

**FM-4 — Waves for the built deploy path.** Cohorts derived from site and node-class, declared halt criteria (≤ a dozen), automatic halt, `maxUnavailablePartitions: 0` semantics, unknown counted against promotion. This is the §6.1 extension of ADR 0224 past §3.6, realized.
*The site disruption budget — §6.7's adoption 2, and the concept FM-4 and FM-6 share.* One invariant, declared once per site and consumed by anything that would disrupt it: **declared by whoever owns the service rather than by whoever wants to disrupt it; a disruption that would violate it stalls visibly and indefinitely rather than proceeding; and an already-unhealthy instance is never counted as a free disruption slot.** For a three-Orin site (ADR 0826) the concrete form is "at least 2 of 3 remain up," answerable from site-local state alone and therefore island-safe. Waves express it as flightctl does — an ordered `{selector, limit, successThreshold}` sequence where the threshold is P12's declared fraction of positive confirmation.
*What this absorbs, so it is not built twice.* A **reboot is a wave of blast unit `node`** against the same budget — it is not a separate mechanism and does not get its own agent. The tree's current defect is real and evidenced: `ops/ansible/mgmt-host-baseline.yml` stats `/var/run/reboot-required` and reboots on it with no serialization, no health gate and no window, and `serial:` appears exactly once in all of `ops/ansible/` (`coordinated-upgrade.yml:206`), so a run against a multi-node group reboots every marked node at once. The interim fix needs no new substrate — `serial:` plus a health gate on the play that already exists — and FM-4 subsumes it. The kured mechanics worth carrying into the implementation are narrow: a lock TTL that is **mandatory** rather than optional (a 30-day islanded site has nobody to clear a stuck lock) and a jittered poll under P9.
*Gate to in-flight:* one real deploy runs as a two-wave sequence with a declared halt criterion, and the site's budget is declared as data rather than assumed by the disruptor.
*Gate to canon:* a wave halts automatically on an induced regression, and the halt is visible without an operator watching.

**FM-5 — Sign the intent document.** Reuse the name-snapshot pattern exactly: monotonic serial, declared TTL, detached signature by the site's existing offline CA, five-state staleness grading, `expired` and `unverified` both refuse. No new key infrastructure.
*Why here and not earlier:* it is only meaningful once there is an intent document a node fetches (FM-2). Doing it before that is signing a file nobody reads.
*Gate to in-flight:* the signer and the node-side verifier land; verification failure is demonstrated to refuse and report diverged rather than proceed.
**Substantially built 2026-08-04 as CF-5** (`consistency-foundation.md` §3.4) — the sequencing argument above was overtaken by the artifact acquiring readers before FM-2 gave it a fetcher: the rollup meter, the applied-intent stamp and the CI gate all read the committed file, so signing stopped being "a file nobody reads" at CF-3. Landed: `ops/enrollment/cmd/intent-sign` (the name-snapshot machinery verbatim), both goatnets' artifacts signed, verify-at-read fail-closed in every consumer in both grammar languages, refusal demonstrated red-then-reverted and pinned as tests. Still FM-2's: the node-side pull-loop verifier and the staleness grading of a *fetched copy* against the artifact's declared TTL — a mgmt-host reading its own deployed copy has no copy-age to grade.

**FM-6 — Generalize the remediation shape.** `netbird-boot-selfheal`'s contract — probe a precise failure signature, act, cool down, cap attempts, escalate — applied to a second failure class, replacing the unbounded serial SSH fan-out in `peer-recover.sh` with a bounded, jittered, per-node loop.
*Required property — the same site disruption budget FM-4 declares, read against remediation instead of against change.* The existing contract caps remediation **per node**; nothing caps the **fraction of a site remediating at once**. A bad pin or a bad render makes every node fail its probe simultaneously, and an uncapped self-heal loop then remediates the entire site — the M-085 storm shape reached from a direction P9 does not cover, since P9 governs load decaying under failure and this governs action volume under *correlated* failure. Cluster API's `MachineHealthCheck` states the rule: remediate only while the unhealthy count is below a declared bound, and do nothing above it, because "one node is broken" and "the world is broken" demand opposite responses. This is why FM-4 and FM-6 do not each get their own guard — it is one budget with two consumers. Note the inversion this project owes: CAPI's guard defaults to 100%, i.e. off; this one ships **on with a conservative bound**, and a remediation loop without a declared bound does not satisfy FM-6.
*Gate to in-flight:* one additional failure class covered, `peer-recover.sh`'s fan-out is bounded and jittered, and every loop declares its correlated-failure bound.

**FM-7 — Islanded intent origination and rejoin reconciliation (P3).** Last, deliberately. It is the hardest problem in the doc, no product in the survey solves it, and it is worth nothing until FM-1 through FM-5 make islanded state observable and signed.
*Gate to backlog→in-flight:* a written per-fact reconciliation policy for at least one operation class. Not before.

Deferred, and named so they are not silently forgotten: an `integration-matrix.md` tier row and the `environment-health-surface.md` domain rows land **when the mechanisms do** (FM-1), not now — the matrix and the domain table describe what exists.

### Complexity budget accounting

Per [ADR 1016](../adr/1016-complexity-budget-substrate-encapsulation.md) D2/D7, stated rather than deferred to a runbook (which that ADR names as an anti-pattern):

- **5-minute path** (`git clone && make bringup`): unchanged. Nothing in FM-1 through FM-6 is on it.
- **30-minute path** (one operator, one playbook, one host): unchanged through FM-3. FM-2 adds one group_var (whether the pull loop is enabled), default off.
- **1-day path** (second site + federation): FM-4 adds one concept — the wave — at the point where a second site first makes waves meaningful. That is the one net-new operator concept in this roadmap.
- **1-week path** (troubleshooting): FM-1 adds a branch to the *existing* decision tree ("node reports diverged, or has not reported") rather than a new tree. That is the constraint on how it may be built.

Consumer-facing substrate count does not increase through FM-3; FM-4 is the first increment that does, and it owes a leak-register entry in its own change-set. The register exists since 2026-08-04 — `docs/leaks/`, created by CF-6's change-set under the same D7 obligation (entry L-001) — so FM-4's obligation is now an entry in an existing register, not a register to invent.

### DIL declaration

Per [`minimalism-under-network-constraints.md`](https://github.com/usareur-af/goatdocs/blob/main/docs/design/minimalism-under-network-constraints.md), which requires each adopting surface to declare the regimes it serves:

- **Disconnected:** the node converges against the site-local replica and reports nothing outward. Its own state is correct and locally observable; fleet-wide visibility of it is `unknown(age)`, never green.
- **Intermittent:** the pull loop's jittered backoff means a node that gets a window uses it; reports queue and replay in order.
- **Low-bandwidth:** intent is a small document and reports are small; neither carries payload. The one deviation from the doctrine's ride-operational-traffic rule is the interval poll, bounded by P9 (§2).

## 8. Adoption guide for a partner goatnet

Written for an organization standing up its own goatnet or attaching its own nodes. The order matters more than the completeness: each step is useful alone, and each is a prerequisite for the next.

**Adopt in this order.**

1. **One pin file, one generator, one CI check.** Every image and release reference in one committed file, rendered into the per-environment files that consume it, with a `--check` job that fails when regeneration is not clean, and an explicit `reason:` field for deliberate deviations. Nothing else on this list works without it, and it is a day's work. *Rules it implements:* P5, P6.
2. **A deploy ledger on every deploying role, and one rollback command.** An append-only per-component record on each host of what was applied, from what version of intent, when, and what the rollback target is. One command that reads it. Refuse to "roll back" data, certs, or schema — point at restore or rotate instead. *Rules:* P13. *This is the highest-value step and it is deliberately second, not last* — the undo primitive should exist before the automation it protects.
3. **A health envelope with a not-reported state.** One envelope, self-published per node, with five grading states where a node that has not reported is explicitly *not* healthy and every reading carries its sample count and window. A passive reader aggregates; the aggregator's absence must degrade visibility, not the fleet. *Rules:* P1, P15.
4. **Split first-contact from routine convergence.** Two playbooks per environment: one that runs once over an out-of-band transport for a node with no mesh identity yet, and one that runs routinely over the mesh. They are different problems and one playbook doing both will be wrong for one of them.
5. **Only now: pull convergence and waves.** FM-2 and FM-4. They are worth building after 1–4, and close to worthless before — a pull loop with no intent file has nothing to pull, and a wave with no health envelope cannot halt on anything.

**The minimum viable subset is steps 1–3.** An organization that does those and nothing else has answered "what should each node run," "how do I undo a change," and "which nodes are lying to me about being healthy" — which is most of the operational value on this axis.

**What not to build first, and why.**

- **A fleet controller that nodes check in with.** It is the shape every commercial product has, it is the fastest thing to demo, and it makes your sites into caches of a thing they must reach. If your sites are meant to be autonomous, this is the one decision that is expensive to reverse later, because everything you build after it assumes it is there.
- **A maintained node database.** Derive inventory from what nodes declare. A hand-maintained CMDB is stale from the moment the first node is enrolled outside it, and it will disagree with reality exactly when you most need it not to.
- **A SaaS agent.** Setting aside data-sovereignty posture: an agent that reports to a cloud service reports the health of your connectivity to that service, not the health of your fleet.
- **Islanded intent origination (P3).** It is the most interesting property on this list and the one to defer longest. Get sites converging correctly against fleet intent before you let them author their own.

**The two rules to copy even if you copy nothing else.** A node that has not reported is `unknown`, not healthy — if you take one line from this document, take that one. And every fleet loop must place *less* load on the network as failures accumulate; a fixed-interval unjittered retry is a self-sustaining outage waiting for bad weather, and this project has the measurement to prove it.

## 9. Status and gates

Nothing in §7 is built. §4 states per-function maturity with citations, and the mechanisms it credits as live are live for their own stated purposes, not for this doc's.

- **This doc's gate to in-flight:** FM-1 lands its proto and one publishing node class.
- **This doc's gate to canon** (per `canon-vs-speculation-criteria.md`): FM-1 through FM-3 deployed on at least one goatnet, one external verification artifact per increment, a named failure mode per increment, and a stranger able to redeploy from these docs alone.
- **The claim this doc is not allowed to make until measured:** any statement of the form "the fleet converges in N minutes." Per [ADR 1012](../adr/1012-load-testing-discipline.md), no measured ceiling means no production claim, and that applies to convergence latency across 3,000 nodes as much as to throughput. Sized, per ADR 0215, for 6 sites and ~3,000 peers at the design center — not for a fleet that would justify a controller plane.
