# Grafana dashboard suite — proving out the value

**BLUF.** Grafana wasn't underwhelming because it's a weak tool — it was
underwhelming because we'd only ever pointed it at **generic infrastructure**.
Four of the five provisioned dashboards were off-the-shelf imports
(`node-exporter-full`, `blackbox`, `cadvisor`, `named-processes`); only
`goat-audit` was ours. So Grafana faithfully showed us CPU graphs nobody opens
and never answered a goat operational question (is a relay flapping? which
tenant went silent? how many days until the audit bucket fills? is a cert about
to expire?). This suite adds **11 dashboards** that ask goat's questions, plus a
**textfile-collector bridge** that lets Grafana render our *bespoke* probe
output (the relay-health prober) at near-parity with the custom single-file
dashboard. Net: Grafana is the right tool for cross-domain metric trends, SLO,
forecasting, RED, and alert/up meta — and the wrong tool for live wire
inspection, topology, and mesh-down standalone use, where the custom surfaces
(flashlight / panoscope / the single-file relay dash) stay canonical. Both
halves are stated honestly below.

Generated by [`ops/compose/goat-obs/grafana/dashboards/gen-dashboards.py`](../../ops/compose/goat-obs/grafana/dashboards/gen-dashboards.py)
(spec → generator → JSON, the repo idiom). The provisioning loader globs
`*.json` every 30s, so the suite lands on the next `obs.yml` run with no
provisioning change.

## The relay replication — and the insight it surfaced

The custom relay-health dashboard (`ops/relay/health/`) is rich — `:443`
enrollment ok-ratio, real `:3478` STUN, `--deep` throughput/peers/cpu — because
the **prober measures all of that**. Blackbox-exporter can re-derive relay
*reachability* and TCP latency, but it **cannot** do the STUN binding request,
the multi-try enroll ok-ratio over the rathole hairpin, or the SSM deep metrics.

So the way to get Grafana close was *not* to re-probe with blackbox — it was to
**reuse the prober's own measurements**. The prober already writes
`relay-health.json`;
[`ops/relay/health/relay-health-to-prom.py`](../../ops/relay/health/relay-health-to-prom.py)
converts that to `goat_relay_*` Prometheus metrics, dropped into a node-exporter
`--collector.textfile.directory` (the obs host already runs that collector). Validated
end-to-end against the live ZAGROS relays — one fast probe produced 33 valid
series (`goat_relay_up`, `goat_relay_enroll_ok_ratio`,
`goat_relay_enroll_tcp_latency_ms`, `goat_relay_rathole_ctl_up`,
`goat_relay_stun_ok`, `goat_relay_probe_timestamp_seconds`, …), vantage-aware
rollup and staleness timestamp included.

**This is the "we were using it wrong" finding in one sentence:** the moment you
feed Grafana your bespoke probe output via the textfile collector, it renders
your domain signals as well as a hand-built surface — the limitation was always
our *integration*, never the tool. The same bridge pattern applies to the
on-bus surfaces (presence, footprint, the env-health envelopes): a small
Zenoh→textfile (or Zenoh→remote_write) shim would let Grafana render those too.
That's the highest-leverage follow-on.

### Wiring the relay bridge

The relay dashboard reads `goat_relay_*`, which exist only where the bridge
runs. Wherever the `relay-health-probe.timer` runs next to a node-exporter
textfile dir (the `relay-health` role host), add to the timer:

```
relay-health-probe.sh --out /opt/relay-health/www/relay-health.json
relay-health-to-prom.py --in /opt/relay-health/www/relay-health.json \
  --out <node-exporter textfile dir>/relay-health.prom
```

Until that's wired on a host this Grafana scrapes, the relay dashboard reads
"No data" — honestly, not falsely green.

## Are we using Grafana wrong, or is it just not that good?

**Mostly the former, with a real boundary.** Evidence-based, not a vibe:

What we were under-using (all now demonstrated in the suite):

- **Textfile collector** — feed bespoke probe/script output as metrics. This is
  the single biggest unlock; it's what turns Grafana from generic-infra-only
  into domain-aware. (relay-fleet-health)
- **PromQL joins as panels** — the F-177 `goat_expected_vendor unless …`
  reconciliation rendered as a silent-vendor table, not just an alert.
  (fabric-tenants)
- **`histogram_quantile` + heatmaps** — p50/p90/p99 latency and distribution.
  (edge-http-red)
- **`predict_linear` forecasting** — "days until disk / audit bucket full"
  turned into honest stats. (capacity-forecast)
- **`ALERTS` + `up` matrix** — a meta board that catches the co-resident-obs
  failure mode. (observability-self-health)
- **State-timeline** — up/down honesty over time instead of a single green dot.
- **Dashboard-as-portal** — a home that ties the suite together. (incident-home)

Where Grafana genuinely is *not* the right tool for goat (a boundary, not a
misuse — this is why the custom surfaces exist and stay canonical):

- **Live per-sample wire inspection** — flashlight tails actual messages;
  Grafana is time-series aggregates, structurally not a message tail.
- **Topology / graph** — panoscope's force-layout peer/flow graph; Grafana's
  node-graph panel is weak for this and has no live-edge animation.
- **Mesh-down standalone use** — the single-file relay dash runs from a laptop
  when the mesh is down and Prometheus is dead with
  it. Grafana on nova-a dies with nova-a; it can't be the outage-time surface.
- **Honesty-grade semantics** — our env-health envelopes carry a 5-state
  honesty colour (green/amber/red only when grounded, else `idle`
  UNCONFIRMED / `unmetered`) plus a sample-count `n`. Grafana approximates this
  with value mappings + "no data" states, but not the UNCONFIRMED-vs-false-green
  nuance natively. The dashboards here lean on thresholds + "no data" and stay
  honest, but it's coarser than the bespoke envelope.

Secondary contributors to the "felt weak" impression, structural to this
deployment (all reasonable for a single-host trial, all worth revisiting):

- Metrics-only — no Loki, so no log correlation in Grafana.
- 15-day retention, single Prometheus, no `remote_write` — fine for one host,
  but it means no long-horizon history and no fleet view.
- The interesting data lives on the Zenoh bus / in the custom surfaces and was
  never bridged into Prometheus (see the textfile-bridge follow-on above).
